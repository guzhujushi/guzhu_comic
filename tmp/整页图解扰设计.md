# 整页图解扰（P1 的设计与验收）

> 2026-10-15 夜。解决的问题：**装到设备上的 APK 首页 / 详情都有真数据，但阅读器里一页都出不来**。
> 落地件：`backend/descramble.py`（新增）、`backend/descramble_android.py`（新增）、
> `backend/api.py::_download_one`（改）、`backend/paths.py`（加 `IS_ANDROID`）、
> 探针 `android/app/src/main/python/guzhu_probe.py`（加第 11 步）。
> 回归：`tmp/_check_descramble.py`（新增，17 项）。

---

## 1. 症状与根因

**症状**：设备（emulator-5554，跑的就是 `full` arm64 包）上首页、详情页全都有真内容，
**一进阅读器就是一列碎图**（每张 `<img>` 只剩 alt 文本「第 N 页」，页面上看着像目录）。
同时 `files/cache/images/<章节>/` 是**空的**：一张图都没落盘，而且 `files/logs/app.log` 里**没有任何错误**。

**根因是两条叠在一起**：

1. **图源发的整页图是"打过乱"的**：一页按 jmcomic 的规则切成 `num` 条横带再倒着重排，
   不解扰就是一页错位的条带。`num` 由 `JmImageTool.get_num(scramble_id, aid, filename)` 算出来，
   实测同一个章节里每张图都可能不一样（305124 的 00001 是 16、00002 是 4；644911 是 14 / 4）。
2. **jmcomic 的解扰每张图都要过 PIL**。看它在 `jmcomic/jm_client_interface.py` 的
   `JmImageResp.transfer_to`：

   ```python
   if decode_image is False or scramble_id is None:
       JmImageTool.save_resp_img(self, path, need_convert=suffix_not_equal(img_url, path))
   else:
       JmImageTool.decode_and_save(
           JmImageTool.get_num_by_url(scramble_id, img_url),
           JmImageTool.open_image(self.content),   # ← 当函数实参，先算出来
           path,
       )
   ```

   `open_image()` 是**当实参先求值**的 —— 所以哪怕 `num` 算出来是 0、根本不需要解扰，
   **也同样会进一次 PIL**。而图源现在发的就是 `.webp`，**Chaquopy 的 Pillow 轮子里没有 `PIL/_webp.so`**
   （不是一个"加载失败"，是这个模块根本没编进去），于是**每一张图**都在 `Image.open` 上抛
   `UnidentifiedImageError: cannot identify image file`。

   桌面 Pillow 带 webp，所以**这条在桌面上永远暴露不出来**：同一个 `_download_one`，
   PC 上一切正常、安卓上全灭。

**为什么之前一整天没看见它**：`_download_one` 当时是

```python
except Exception:
    tmp.unlink(missing_ok=True)
    return False        # 异常没了，日志里也没有
```

于是"图永远下不下来"在界面上表现为"一直转圈重试"，**服务端一个字都不说**。
这一次顺手补了 `_note_download_failure()`：同一章节第一次失败就打一行 log（不刷屏）。

> 这条也解释了**为什么探针当时是绿的**：探针第 8 步是自己拿 `curl_cffi` 直接下字节，
> 根本不经过 jmcomic 的下载器，所以永远碰不到 PIL。

## 2. 方案：自己收口解扰

思路一句话：**下载那一步只让 jmcomic 落"原图"，解扰自己做**。

```
_download_one(img, path)
   │
   ├─ self._jm.download_by_image_detail(img, tmp, decode_image=False)
   │     └─ transfer_to(path, scramble, False, url) → need_convert=False → save_directly
   │        （后缀一致就纯写字节，**一点不碰 PIL**）
   │
   ├─ descramble.fix_file(tmp, descramble.num_for(img))
   │     └─ band_plan() 算横带计划 → 交给平台解码器就地还原
   │
   └─ tmp.rename(path)
```

**横带规则只有一份实现**（`backend/descramble.py::band_plan`），复刻 jmcomic 的循环：

```
over = h % num
第 i 条（i=0..num-1）：源起点 = h - (h//num)*(i+1) - over，高度 = h//num，目标起点 = (h//num)*i
  特例：i == 0 时高度再加 over，其余各条目标起点整体后移 over
```

**解码器按平台挑**（这是唯一分叉的地方，收在 `_pick_fixer()` 里）：

| 平台 | 用什么 | 为什么 |
|---|---|---|
| 桌面 / 其它 | Pillow：`Image.open` → `Image.new("RGB")` + `crop`/`paste` → `save(原路径)` | 与 jmcomic `decode_and_save` **逐字节同路**，所以替掉它之后桌面产物一个字节都不变 |
| 安卓 | `BitmapFactory.decodeByteArray` → `Canvas.drawBitmap(Rect→Rect, Paint(filterBitmap=False))` → `Bitmap.compress(WEBP, 90)` | 系统自带（跟 Chromium 同一批底层库）**原生支持 webp**；不用 NDK、不用自出轮子、不装任何新依赖 |

安卓这半边**走 Chaquopy 的 Java 桥直接从 Python 调 android.\* 类**（`from java import jclass`），
所以**一行 Kotlin 都不用加**，也不需要改别的构建配置。

细节：

- `num_for()` 直接问 jmcomic（`JmImageTool.get_num_by_detail`），**不自己再实现一遍 `get_num`**，
  免得哪天上游规则变了、两边漂移；拿不到就返回 0（=原样落盘，宁可不解也不赌）。
- `.gif` 一律 0：jmcomic 自己也不解 gif（`decide_download_image_decode` 第一句就是它），
  动图本来就不是按整页横带切的，硬切只会切坏。
- `num<=0` / `num>height` / 尺寸对不上 → `band_plan` 返回空表 → **原样不动**。
- 安卓重编用**有损 webp、质量 90**：源图本来就是有损 webp，桌面那条 Pillow 路用的是默认的 80，
  这里 90 已经不比桌面差；磁盘上一个章节（47 页）大约 15 MB，和 PC 上同一量级。

## 3. 被否掉的路线（都记一笔，免得下次重走）

| 路线 | 为什么不做 |
|---|---|
| **自出带 libwebp 的 Pillow 轮子**（`build-wheel.py` + NDK + 交叉编译 libwebp） | 最"正统"，但要装 NDK（1~2 GB）、要编两遍、失败风险高；而且这套东西**只在出包时用得上**，对用户（无收入、要 0 成本）性价比最低 |
| **`opencv-python-headless`**（Chaquopy 的包源里确实有，imgcodecs 能解 webp） | 查了包源：**只到 `cp310`**（`opencv_python_headless-4.5.1.48-2-cp310-…-android_24_arm64_v8a.whl`），本 app 是 **Python 3.13**，装不上 |
| **在 WebView 里用 canvas 解扰**（`drawImage` 逐条带画到 canvas，再 `toBlob` 喂给 `<img>`） | 前置条件更差：磁盘上留下的会是**打过乱的原图**，于是"整本离线下载""下载页预览""导出"拿到的都是乱图。而且阅读器那套按 `naturalWidth` 排版的逻辑要跟着改 |
| **再写一份 Kotlin 版横带算法**（Python 一侧只调用） | 同一套规则会有两份实现，且 Kotlin 那份**在桌面上没法测**。现在是"规则在 Python（桌面可对拍）、编解码在平台" |
| **关掉 `decode_image` 了事**（不管解扰） | 阅读器会显示一页**错位的条带**，等于没修 |

## 4. 验收（全绿）

**桌面（`tmp/_check_descramble.py`，17 项通过）**

- `band_plan` 在 7 组 `(height, num)`（含 `over != 0`、`num > height` 等边界）下都是**完整置换**：
  源片段与目标片段都严丝合缝铺满 `[0, h)`，不重不漏；
- `num_for` 与 jmcomic 的 `get_num_by_detail` 一致；`.gif` → 0；老本子（`aid < scramble_id`）→ 0；
- **逐字节对拍**：3 部作品 6 张真图（305124 / 644911 / 422866，num 分别是 16/4/14/4/10/14），
  我们这条路的产物与 jmcomic 自带解码的产物 **6/6 逐字节相同** → 桌面缓存文件零变化；
- **走真实下载链路**：`get_chapter("422866")` → 后台下载 → 2 个文件 **3 秒**落盘，
  且落盘那张与"解扰后"一致（条带没错位）；
- `num=0` 时文件一个字节不变。

**桌面整体回归**：`tmp/_runchecks.py` → **30/30 通过**。

**设备（emulator-5554，装的 `full` arm64 包）**

- 探针**第 11 步「系统解码器解扰真图」**：`num=10`，218,914 B → 307,042 B，**0.4 s**（这一步就是安卓那条解码器的活体证明）；
- 把探针产物拉回电脑上图算：设备产物 **vs 桌面解扰** 平均每像素差 **1.71**（只是重编了一次有损 webp）；
  **vs 不解扰的原图 85.06**；逐条带 1.41~2.09（真错位的话会到 80 以上）→ **数值确认条带顺序正确**；
- **肉眼看图**：拉回来的那张是一整页连续画面，条带接缝处没有任何错位；
- **设备手感**：真点进阅读器截图，**整页图正常铺出**；`files/cache/images/<章节>/` 落满真图（292 KB~650 KB/张）。

## 5. 遗留 / 以后可改

- **有损重编一次**：安卓侧是 `WEBP(90)`。想完全无损可以换 `Bitmap.CompressFormat.WEBP_LOSSLESS`（API 30+），
  代价是磁盘大约 ×5~7（一话 47 页会从 ~15 MB 涨到 ~70 MB）。**当前取"与 PC 同一量级"**。
- **iOS / 其它平台**：`_pick_fixer()` 只有"安卓 / 非安卓"两路，将来真上别的平台照这个模式加一路就行。
- **JmImageDetail 的属性口径**：`num_for` 依赖 `img_file_suffix` / `get_num_by_detail`，
  升级 jmcomic 之后要重跑 `tmp/_check_descramble.py`（它会在第一次就对拍出错）。
