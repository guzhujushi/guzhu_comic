## 0. 逐层选型（这就是结论）

## 1. 逐层理由与代价

### 1.1 运行时 = Chaquopy（CPython 进 App 进程）

- **已核实**：Chaquopy **17.1.0 是 MIT 许可**（Maven Central 的 POM 里 `<licenses>` 明写 MIT）。历史版本曾是商业授权，现在不用管。
- **已核实**：17.1 支持 **Python 3.10~3.15**、**最低 Android API 24**、支持的 AGP 版本 **7.3~9.4**；最新版 17.1.0 发布于 **2026-10-12**。
- **已核实**：Chaquopy 17.0 起 pip **只用 `--only-binary`**（只装 wheel，sdist 一律不装）→ 任何一个没有安卓轮子的依赖都会在构建时当场失败。这条是本方案的总闸（§4-T1）。
- **代价**：要装 Android SDK + Gradle 工具链（§5）；调试循环从"双击 `main.py`"变成"重装 APK"；APK 体积估 **40~60 MB**（主要块：curl_cffi 的 `.so` 22.9 MB + Python 运行时 ~12.6 MB + Pillow/pycryptodome）（比桌面 zip 20 MB 大一倍多）。
- **为什么不选 p4a + Kivy**：pywebview 自带的 android 后端建在 Kivy Activity 上（`webview/platforms/android/app.py` 里 `from android.activity import ...`，**已核实**包内源码）—— 等于同时背 Kivy 和 WebView 两套 UI 栈，而且 p4a **只在 Linux 构建**；它对"要安卓轮子"的诉求和 Chaquopy 一模一样，却没有 Chaquopy 那套包仓库。

### 1.2 UI 壳 = AndroidX WebView（不引入任何前端框架）

- 现有 `frontend/dist` 是纯静态产物 + 一手 hash 路由 + 原生 DOM，**WebView 里直接能跑**；CSS 用的都是保守特性（`aspect-ratio` / `backdrop-filter` / `clip-path`），没有 `:has` / `@container` / `oklch` 这些新内核专属的东西 → 兼容性风险低。
- **不选 Capacitor / Cordova**：它们只解决"Web ↔ 原生"的 JS 桥，**不会把 Python 带进来** —— 用了还得再上 Chaquopy，白多一层抽象和一份依赖。
- **不选 GeckoView**：包体 50 MB+、非系统组件、升级要自己发版；我们没有任何必须换内核的理由。
- **不选原生 Compose 重写**：等于把 5715 行 TS + 69 KB CSS 重来一遍，收益只有"更原生"，代价是几个月。

### 1.3 桥 = 本地 HTTP JSON-RPC

- **前端侧**：写一个几十行的垫片，把 `window.pywebview.api` 造出来（`fetch('http://127.0.0.1:<port>/api/<method>')`），再派发一次 `pywebviewready` → **51 处 `window.pywebview` 引用一行都不用改**（`webstatus.ts` 那套 `waitForBridge` / `bridgeCall` 保留，垫片是同步挂好的，会立刻通过）。
- **后端侧**：`backend/server.py` 本来就在跑静态服务（打包态就是"页面与图同源"），加一个 `POST /api/<method>` 只是多一个 handler 分支；方法分发用 `getattr` + **显式白名单**（54 个公开方法；别重蹈 `API.client` 被 `dir()`+`getattr()` 展开成 412 个方法的覆辙）。
- **为什么不用 `addJavascriptInterface`**：每次调用跨 JS→Java→Python 三层、大 JSON（一话 200 个 URL）序列化两次、`@JavascriptInterface` 方法跑在非 UI 线程；而且要在 Kotlin 侧维护 54 个方法的映射表，改接口要动两个语言。
- **安全（顺手要补的洞）**：安卓上**同设备的任意 app 都能访问 127.0.0.1**（桌面至少还有 Host 白名单挡 DNS rebinding）→ 启动时生成随机 token，`/api` 校验；桌面版本同样受益。
- **明文放行**：WebView 加载 `http://127.0.0.1` 属于 cleartext，Android 9+ 默认禁止 → 用 `network_security_config` **只**给 `127.0.0.1` / `localhost` 开口子。

### 1.4 Python ↔ Android 集成 = Chaquopy 的 `java` 模块

- **已核实**（官方 Python API 页）：Python 侧有 `java` 模块，Java 对象在 Python 里就是 `jclass` 对象，原始类型可自动装箱/拆箱，还有 `cast` / `jarray` / `static_proxy`。
- **意义**：`desktop.py` 那 512 行的门面化改造，可以在 **Python 侧**用 `jclass` 直接拿 `Context`、`StatFs`、`NotificationManager`、SAF 的 `Intent`，不必把逻辑搬进 Kotlin。这能省掉一大块跨语言样板。
- 反过来（Kotlin → Python）用 `Python.getInstance().getModule("backend.api")` + `PyObject.callAttr(...)`，只在**壳的启动路径**上用（起服务、注入路径、生命周期回调）。

### 1.5 构建链与版本线（**2026-10-15 第一次真构建后整节重写**）

> 原来写的是 AGP 8.13.2 + Gradle 8.14.6 + `.venv`(3.14)。**2026-10-15 实跑 `gradlew` 之后全部改判** —— 理由都是本机实测或官方兼容表，不是偏好。

**版本线（现在钉的是这个）**

| 项 | 值 | 依据 |
|---|---|---|
| Gradle 用的 JDK | **Android Studio 自带的 JBR 25.0.3** | Android Studio（build `AI-262.9437.185.2621.16467767`，装在 `D:\Andriod Studio` —— 目录名就是 `Andriod`）自带的 JBR 是 **Java 25**（旧文档写的 "JBR 21" **已过期**）；系统那个是 **Oracle JDK 26.0.1**，AGP 未必认，别用 |
| Gradle | **9.8.1** | Gradle 官方兼容表：**Java 25 跑 Gradle 要求 ≥ 9.1** → 原定的 8.14.6 在这台机器上直接出局 |
| AGP | **9.4.0** | 从 AGP 9.4.x 包里挖出 `VersionCheckPlugin.GRADLE_MIN_VERSION`：**AGP 9.4 要求 Gradle ≥ 9.6.0** → 9.8.1 满足；且 9.4 正好压在 Chaquopy 17.1 的支持上沿（7.3~9.4） |
| Kotlin 插件 | **不挂**（`org.jetbrains.kotlin.android` 已从 `plugins {}` 摘掉） | **AGP 9 起 Kotlin 内置**；再显式挂一个 Kotlin 插件 = 版本冲突、构建**硬失败**（本轮第一次 `assembleDebug` 就是这么挂的） |
| 构建机 Python | **Python 3.13**（另装，**不是**仓库 `.venv` 的 3.14.6） | 见下一节 |

**为什么必须降到 Python 3.13（2026-10-15 逐包联网核过）**

Chaquopy 的安卓原生轮子只有**一个**仓库：**`https://chaquo.com/pypi-13.1`**（构建日志里实际用的就是它；`pypi-12.0` / `13.0` / `14.0` / `15.0` / `16.0` / `17.0` / `pypi` 全部 **404**）。

把 `android_24_arm64_v8a` 的轮子逐个列出来看 python tag：

| 包 | 这个仓库里 arm64_v8a 的 cpXX | 最高版本 | 有 cp314 吗 |
|---|---|---|---|
| `cffi` | cp38/39/310/311/312、**cp313** | 1.17.1 | **没有** |
| `pillow` | cp38/39/310/311/312、**cp313** | 11.0.0 | **没有** |
| `pycryptodome` | cp38/39/310/311/312、**cp313** | 3.21.0 | **没有** |
| `pyyaml` | cp310/311/312、**cp313** | 6.0.3 | **没有** |

→ **3.14 一个原生轮子都拿不到**。本轮 `assembleDebug` 报的 `ERROR: Could not find a version that satisfies the requirement pillow (from versions: none)` 就是这个（当时构建机 Python 是 `.venv` 的 3.14.6）。**3.14 这条路作废，改 3.13。**

`curl_cffi` 反过来是通的（它在 PyPI，不在 Chaquopy 仓库）：

| 版本 | `android_24_arm64_v8a` 轮子的 cpXX |
|---|---|
| 0.15.0 / 0.15.1 / 0.16.0 / 0.16.1 | cp313 |
| 0.16.2 / **0.16.3** | **cp313 + cp314** |

注意 **0.14 及以前一个安卓轮子都没有** → 「降 curl_cffi 版本来躲开 cffi 2.0」这条退路**不存在**。

**cffi 堵点（本轮最重要的发现）**

- `curl_cffi` **0.15.0 起每一版**都声明 `cffi>=2.0.0`（逐版本查 PyPI metadata：`0.15.0b2` / `0.15.0` / `0.15.1b2` / `0.16.0` / `0.16.1` / `0.16.2` / `0.16.3` 全是）；
- 而**安卓上不存在任何 cffi 2.x 轮子**：Chaquopy 仓库到 **1.17.1** 封顶，**PyPI 上 cffi 全系 0 个安卓轮子**（`2.0.0` / `2.1.0` / `2.1.1` 只有 iOS / macOS / Linux / Windows）；
- `curl_cffi/__init__.py` 里写死 `import _cffi_backend  # required by _wrapper`，`.so` 里也有 `_cffi_backend` 字符串 → **cffi 运行时必需，省不掉**。

**唯一的绕法**：显式锁版本 + `--no-deps`（让 pip 不去读 `curl_cffi` 的依赖声明）。`android/app/build.gradle.kts` 里已经是这么写的，并且用 `pip --dry-run` 验过解析能过：

```kotlin
chaquopy { defaultConfig { pip {
    options("--no-deps")
    install("cffi==1.17.1")        // 被 curl_cffi 声明要 >=2.0.0，这里硬压回 1.17.1
    install("certifi")
    install("curl-cffi==0.16.3")   // cp313 的 android_24_arm64_v8a 轮子
    install("pillow==11.0.0")
    install("pycryptodome==3.21.0")
    install("pyyaml==6.0.3")
    install("jmcomic==2.7.9")
    install("commonx==0.6.40")
} } }
```

**代价 / 未验的风险**：`cffi 1.17.1` 的 `_cffi_backend` 与 `curl_cffi 0.16.3` 的 `_wrapper.abi3.so` 在 **C ABI 层面兼不兼容，没有验证过**（作者声明 2.0.0 起步，说明他认为 1.x 不够）。这是 **T1 剩下的唯一未知**，只能在真机上撞一次（§4）。真撞死了的三条退路：① 自己给 `curl_cffi ≤0.14` 出安卓轮子（成本高）；② 换 Chaquopy 仓库里的 `chaquopy-curl`（curl 7.76.1 老绑定、**没有浏览器指纹**，图源大概率拦）；③ 退 R1 瘦客户端（后端留在 PC）。

**compileSdk 36 → 37（2026-10-15 实跑后改）**：`androidx.core:core:1.19.1` / `core-ktx:1.19.1` 在 `checkDebugAarMetadata` 里明确要求 **compileSdk ≥ 37**。只动 `compileSdk`（`targetSdk` 仍 36 —— Play 的门槛是 targetSdk，compileSdk 只影响「能编到哪些 API」）。

**其余不变**：minSdk 26 / targetSdk 36 / 只出 `arm64-v8a`；Chaquopy 只装预编译 wheel（它自己通过 `target-3.13.x-0-arm64-v8a.zip` 提供 `libpython3.13.so`），**理论上不需要 NDK**。
### 1.6 后台下载 = 前台服务（`dataSync`）

- **已核实**（官方服务类型表）：`dataSync` 的适用场景明写包含 **"Data upload or download"**，需要在 manifest 声明 `android:foregroundServiceType="dataSync"` + `FOREGROUND_SERVICE_DATA_SYNC` 权限，**Runtime prerequisites: None**（不需要额外运行时权限）。
- **已核实**（官方超时文档）：**Android 15 起，`dataSync` / `mediaProcessing` 前台服务在 24 小时内累计只能跑 6 小时**，到点系统调 `Service.onTimeout(int, int)`。
- **设计后果**（这条会反过来影响实现）：整本下载（几百 MB、可能跨天）必须在 `onTimeout` 里**优雅收尾**（把进度落库 → 停服务 → 通知用户"下次打开自动接着下"），而不是硬跑。现有"进度以磁盘为准 + 重启只补缺的"那套设计正好扛这个，是提前做对的地方。
- **为什么不用 WorkManager**：它适合"几分钟内跑完的小任务"，有 10 分钟级别的执行窗；几百 MB 的整本下载会被反复打断重排。

### 1.7 存储与权限

现有 `~/.jmreader` 里的三块在安卓上各归各的（都能在 `backend/paths.py` 一处收口）：

| 现在 | 安卓 | 说明 |
|---|---|---|
| `data/`（sqlite：进度 / 收藏 / 搜索记录 / 下载任务单） | `getFilesDir()` | 卸载即清，符合"用户数据"的语义 |
| `cache/`（章节图、接口缓存） | `getCacheDir()` | 系统空间紧张时会**被系统自己删**（比现在按 2 GB 上限清理更狠，但语义更对） |
| `downloads/`（离线副本，用户数据、几十~几百 MB） | `getExternalFilesDir()`（默认），可选 SAF 目录 | 默认值要改小（`cache.max_size_mb` 2048 → 512~1024） |
| 导出 / 导入 / 挑文件 | **SAF**（`ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`） | `api.py` 的 `create_file_dialog` 现在直接 `import webview`，要换 |

另外 `get_disk_usage` 用的 `shutil.disk_usage`（`api.py:2017`）在安卓上读到的是 root 分区，要换 `StatFs`（可用 §1.4 的 `jclass` 直接调）。

### 1.8 网络

- **运行期不需要科学上网**（`tmp/STATUS.md`「直连可用性实测」已经验过），安卓上同理；`curl_cffi` 自带的 Chrome 指纹就是过图源门槛的那把钥匙。
- 唯一要声明的是 `INTERNET` 权限（普通权限，安装即得，不弹窗）。
- 图源域名会在 `www.cdnhjk.net` / `www.cdngwc.*` 之间轮换，`api.update_domain` 那套逻辑照旧。

## 3. 已核实的关键事实（证据汇总）

**安卓工作区的落地方式（2026-10-15 已建）**

- `android/` 是 Gradle 工程（AGP 9.4.0 / Gradle 9.8.1 / **不挂 Kotlin 插件** / Chaquopy 17.1.0 / 构建机 Python 3.13 —— 见 §1.5），`app/build.gradle.kts` 里的 `chaquopy { defaultConfig { version = "3.13"; buildPython(<另装的 Python 3.13>) ; pip { options("--no-deps"); ... } } }` 就是 §1.1/§1.5 那套的落笔（DSL 形态在 Chaquopy 17.1 官方文档里核实过）。
- **迁移不靠 Gradle**：`backend/` → `android/app/src/main/python/backend/`、`frontend/dist` → `android/app/src/main/assets/web/`，都用 `scripts/sync_android.ps1` 拷贝（两边 gitignore）。判断依据是既有代码的 import 风格：`from backend.api import API` —— 副本目录必须叫 `backend/`，所以不能让 Chaquopy 的 `srcDir` 直接指仓库根。
- 壳现在**已经接上真前端**：`assets/web/` → 解包到 `filesDir/dist` → Chaquopy 起 `backend/server.py`
  → `WebView.loadUrl("http://127.0.0.1:47753")`。**2026-10-15 在 x86_64 模拟器上跑通并截图**（见下）。
  另外确认了一条此前未验的：**`backend/` 是隐式命名空间包（没有 `__init__.py`），Chaquopy 的 importer 能正常 import**。

**curl_cffi 的安卓轮子（我在本机下载解包实测）**

| 项 | 结果 |
|---|---|
| 轮子 | `curl_cffi-0.16.3-cp314-cp314-android_24_arm64_v8a.whl`，8.21 MB，上传于 **2026-09-02**（另有 cp313 同款） |

## 5. 安卓「环境」到底要解决什么 —— 三层，别混（2026-10-14 实测）

写这一节的原因：「安卓环境」这四个字在三件不同的事上都被用到，混在一起就会得出"要往手机里装 sshd"这种结论。**其实这三层互不相干**：

| 层 | 是什么 | 在哪儿 | 手机要做什么 |
|---|---|---|---|
| ① **构建环境** | JDK + Gradle + Android SDK + Chaquopy 插件 → 把 `backend/` + `frontend/dist` 打成 APK | **PC 上** | **什么都不用做** |
| ② **连接/调试通道** | `adb`：装包、看日志、`chrome://inspect` 调 WebView | PC ↔ 手机（USB 或无线） | 打开「开发者选项 → USB 调试」（无线调试是系统自带的，见 5.2） |
| ③ **运行设备** | 装上去真跑：验图源连通、长图渲染、后台下载 | **一台 arm64 真机** | 提供设备（见 5.3 为什么非真机不可） |

### 5.2 连接/调试通道：`adb` 就够 —— **不需要 sshd、不需要 root、手机上不装任何东西**

- **sshd 是"把手机当远程服务器"用的**（Termux 里跑服务、从别处 ssh 上去）。我们的场景是"PC 编、手机跑"，正规通道是 **`adb`**：
  - **USB**：手机打开「开发者选项 → USB 调试」→ 插线 → `adb devices` 就能看见（最稳）。
  - **无线（Android 11+）**：开发者选项里的「**无线调试**」→ 配对码 → `adb pair` + `adb connect`。**这同样是系统自带的，不用装 sshd**（比老办法 `adb tcpip 5555` 干净，不需要先插一次线）。
  - 所以**手机侧唯一要做的事：打开开发者选项与 USB 调试**（个别国产 ROM 还要打开"USB 安装"或登录厂商账号，仅此而已）。
- 调前端：`WebView.setWebContentsDebuggingEnabled(true)` + PC 上 Chrome 打开 `chrome://inspect` → 直接调页面（体验接近桌面 WebView2 的 DevTools）。
- 装包：`adb install -r app-debug.apk`，或者把 APK 拷进手机点击安装（首次要允许"未知来源"）。

### 5.3 运行设备：~~最终要一台 arm64 真机~~ —— **本节原结论已被 2026-10-15 晚的实测推翻一半**

> 真机只剩 T3~T6 那类跟手感 / 内存 / 国产 ROM 保活有关的 —— **模拟器的性能基线 ≠ 真机，那几条拿它测不算数**。
> 另外：翻译层只有 **arm64 代码 → x86_64 内核**这一个方向，**别拿它的速度当性能结论**。

  - arm64 系统镜像**是有的**，而且**一直到 API 37 都有**（`system-images/android-36/google_apis/arm64-v8a`、`system-images/android-37.0/google_apis/arm64-v8a`）。

#### 5.3.1 0 元能解锁到哪一步（2026-10-15 定）

把「验 R2 的依赖」和「验 UI / 壳」拆开看，结论完全不同：

| 要验的 | x86_64 模拟器 | 说明 |
|---|---|---|

| P2 壳接 `127.0.0.1`、返回键链路（T7） | **行** | 与 ABI 无关 |
| T3 / T4 / T6（长图渲染上限、一话 200 张图内存、毛玻璃掉帧） | **行** | 注意模拟器的性能基线 ≠ 真机：只能看「有没有崩 / 有没有量级问题」，看不了真实手感 |
| T5（前台服务保活 / `onTimeout`） | **部分行** | 能验逻辑与收尾；验不了国产 ROM 的杀后台行为 |
| T8（同机 app 读 `127.0.0.1`） | **行** | 在模拟器里起个浏览器试就行 |

**做法**：给 `android/` 加一个「UI 变体」—— `abiFilters` 改 `x86_64`，pip 列表里去掉 `curl_cffi`（连 `jmcomic` 一起去掉），换成一个明确报错的桩模块；然后 `assemble<变体>Debug` → `adb install` 进 x86_64 模拟器 → 把壳、路由、触屏布局、长图渲染、内存全验一遍。`curl_cffi` 那条真机验证继续等设备。

**代价**：多一个 flavor，构建矩阵变 2 条；好处是**在没有任何安卓设备、0 元的前提下，把 P2 / P3 和 T3~T7 的一大半解锁掉**。

**2026-10-15 晚：这条路已经走通（`ui` 变体实测）**

- `:app:assembleUiDebug` → **BUILD SUCCESSFUL**，`app-ui-debug.apk` = **29,004,046 B（≈27.7 MiB）**
  （比 `full` 的 35.71 MB 小 —— 少的就是 `curl_cffi` 那 24 MB 的 `_wrapper.abi3.so`）。
- `adb install` + `am start` → **真前端渲染出来了**：左侧导航栏、「热门榜单」、搜索框、分类 chips 全在
  （截图 `tmp/_ui/p2-1-board.png`）。数据区是前端自己的优雅错误态「加载失败了 / pywebview api 还没就绪」
  —— **P0 的 HTTP 桥还没做，这是预期结果**。
- **触屏导航 + 返回键（T7）通**：点导航进搜索页 → 软键盘正常顶起（`adjustResize`）→
  第一次返回收键盘 → 第二次返回回到榜单页（hash 历史 + `goBack()`，同一文档内穿梭，没重新加载）。
- **PC 侧穿过 `adb forward tcp:47753 tcp:47753` 直连设备里的服务**：`GET /` 200 / 5618 B、
  `GET /assets/index-*.js` 200 / 128150 B、`/nope.html` 404、`Host: evil.example.com` → **403**
  （Host 白名单在安卓上照样生效）。
- **它验不了什么（别误判）**：`ui` 变体在 x86_64 上**永远拿不到 `curl_cffi`**（那是个一调就抛的桩）—— 但**要验 T1 / T1-b / T2 不必换真机**：装 `full` 变体（arm64）就行，模拟器自带 ARM 翻译层（2026-10-15 晚实测，见 §5.3 开头）。
- **它暴露了什么**：版式还是桌面那套（1080px 宽的手机上左栏挤得「周榜 / 按观看」两个下拉折成三行）、
  搜索页自动聚焦弹键盘 —— 都是 D6「触屏 UI」那一轮要改的，见 `可行性评估 §D6`。


### 5.4 手机侧要求（checklist）——**注意：手上这两台都不满足**

- Android **8.0+**（API 26+；技术上 24 也行，但按 §1.5 定的 26）
- **arm64** CPU（2016 年之后的机器基本都是）
- 开发者选项 + USB 调试（无线调试需 Android 11+）
- 空闲存储 **≥ 2 GB**（APK 40~60 MB + 缓存 + 一话 200 张图）
- 允许侧载（未知来源）
- 建议**用 Wi-Fi 做下载测试**（整本几百 MB，别拿蜂窝流量烧）
- ⚠️ **先确认这台能装 APK**：不是所有华为 / 鸿蒙机器都行 —— 见 §5.7 的本机实测（现在插着的那台 Mate 80 Pro 是 HarmonyOS 6，**装不了 APK**）。

### 5.5 设备怎么安排（**2026-10-15 更新：原来的前提已经不成立**）

原来假定手上有两台安卓机。**实际情况是：一台 Mate 80 Pro（HarmonyOS 6，装不了 APK、也没有 ADB 端点）+ 一台 iPhone（另一套系统，代码零复用）** → 两台都当不了测试机（见 §5.7、§5.3）。

所以现在的设备策略是：

- **首选**：弄一台**便宜的二手 arm64 安卓机**（Android 8.0+ 就行）—— 这是唯一能一次到位跑完 T1~T7 的路。
- **次选**：**arm64 模拟器（API 33/34 的镜像，别选 x86_64）**，只用来验 T1 / T1-b / T2 这几道「装得上、连得上」的一次性结论。
- **留一台固定当测试机**：插着线（或常开无线调试），反复装 / 卸、跑整本下载都在它身上。
- **优先用较弱 / 较旧的那台做验收** —— 低端机过关才算真过关：长图渲染、一话 200 张图的内存、后台被杀，这些压力只有弱机才暴露得出来；在主力机上测出来的"没问题"很容易是假象。
- 主力机留到最后"日常用着顺不顺手"那一次（手感 / 真实使用场景）。

### 5.7 本机 USB 实测（2026-10-15）—— 现在插着的那台**当不了测试机**

> 全部是这台 PC 上的实机查询结果，不是推测。命令、原始输出、排障办法见 `tmp/安卓真机连接与调试操作手册.md`。

| 名称 | `HUAWEI Mate 80 Pro`（手机自报） |

读出两件事：① **华为这两次接入一次 ADB 接口都没出现**（只有 MTP + Mass Storage）→ 这台机器从没开过 USB 调试；就算开了，华为鸿蒙线给的是 `hdc`，`adb devices` 也不认。② **唯一被枚举成 `ADB Device` 的是那台讯飞墨水屏电子书**（`VID_2207` = Rockchip，arm64）→ 能当「验 T1 总闸」的备选（墨水屏验不了 UI / 性能）。

**为什么这台 Mate 80 Pro 当不了测试机（三条）**

1. **装不了 APK**：Mate 80 系列 2025-11-25 上市，**全线 HarmonyOS 6**；鸿蒙 5 / NEXT 起改用鸿蒙内核、去掉 Linux 内核，**只支持鸿蒙原生应用，不能原生运行 Android 应用**（官方口径：不属于 Android，不与 Android 应用兼容；第三方容器「卓易通」「出境易」能跑，但那是别人的兼容层，不是我们的验收环境）。
2. **ADB 端点不存在**（见上表）→ 没有 `adb install` 这条路。
3. **存储布局也是鸿蒙的**（`HO_DATA_EXT_MISC`、`图库`，没有 `Android/`）。

**结论 / 待办**

- Mate 80 Pro 这台**不作为安卓测试机**（除非从「设置 → 关于手机」确认它其实是能装 APK 的 HarmonyOS 4 —— 但那与「Mate 80 全系 HarmonyOS 6」冲突，基本不用抱这个希望）。
- **待用户确认**：第二台手机是什么型号 / 系统、能不能装 APK —— 这是 P1 开工前的硬前置条件。
- 机器定了以后，照 `tmp/安卓真机连接与调试操作手册.md` 走一遍（PC 装 SDK / `adb` → 手机开 USB 调试 → `adb devices` 认出来 → 几条 `getprop` 核验），再动 `android/` 骨架。
