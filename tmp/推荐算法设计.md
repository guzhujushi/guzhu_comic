# 推荐算法设计（一期）—— 按收藏 / 搜索的 tag + 作者匹配

> 依据：`tmp/交接文档.md` §2/§3、`tmp/STATUS.md`（已做的预加载）、用户 2026-10-14 的口径与批复。
> 状态：**一期已实现（2026-10-14）**。施工前请对照 §14：那里记了落地细节与跟设计稿的小偏差。

## 0. 一句话

每次推荐都从**热度榜**拉一批候选（默认 40 部），用「收藏 + 搜索」攒出来的 **tag / 作者画像**给候选打分，取前 N 铺在首页和搜索页。
全部在后端本地算（sqlite 读缓存 + 内存打分），**推荐本身几乎不开新请求**（复用首页已经在拉的榜单缓存）；画像为空就退化成热门。

## 1. 画像（taste profile）

| 来源 | 权重 | 怎么拿 |
|---|---|---|
| 收藏 | tag 每部 1.0；作者每部 1.0 | `favorite.tags_json` / `favorite.authors_json`（加收藏那一刻的快照，见 §2）；老行没有就回落到详情缓存 |
| 搜索关键词 | 每次 0.6 | 关键词**直接当 tag / 作者字符串**参与匹配（「中文」「同人」本来就是 JM 的 tag；搜作者名就命中作者维度；搜作品名两边都不命中，天然无害） |

- **不做隐式反馈**（点开详情那档，用户 2026-10-14 明确砍掉）。
- 累加：同一个 tag / 作者出现几次就加几次。
- 时间衰减：`w *= 0.5 ** (age_days / recommend.half_life_days)`（默认 30 天）。
- 归一化：tag 与作者各自除以自己的最大权重，只留 **top 20 tag + top 10 作者**。
- 画像**不落盘**：每次现算（输入全在本地库里）。

## 2. 收藏行的快照（一处小改，但很关键）

详情缓存 TTL 只有 24h，靠它算收藏的 tag / 作者，一周后画像就空一半。
所以 `favorite` 表加两列 `tags_json` / `authors_json`：加收藏时顺手存（进详情页本来就拿着 tags 与 authors，多传一个参数）；
`ALTER TABLE ... ADD COLUMN` 兼容老库，老行缺就跳过、下次进详情页再补。

## 3. 候选池

- `get_ranking('week', 'all', page=1..P, order_by='views')`，P 由 `recommend.candidates`（默认 **40**，2 页）算；走现成的 `ranking:*` 缓存（TTL 1h）。
- **候选池大小不是速度旋钮，是覆盖度旋钮**：
  - 榜单请求：首页本来就在拉（hero 的 `all` 页 1 + 各分类榜），推荐复用的就是同一批；冷缓存时最多多 1 次（页 2）。
  - tag / 作者：从**本地 sqlite 详情缓存**取（微秒级），没缓存的候选**直接跳过**，绝不在这条路上发请求。
  - 所以"启动慢"不会发生；而且推荐段是**异步铺**的 —— 不挡 hero 与分类横条，失败 / 慢了整段藏起来。
- tag / 作者只从**详情缓存**取 → 「列表铺完预热详情」那套（2026-10-14 已做）就是推荐的地基；**收藏页也要补上预热**（一期一起做）。
- 过滤：`换一批` 时把本段已展示的 ID 传回来排除。**已收藏的不排除，打角标**（§6）。

## 4. 打分

```
热度(item) = 1 - 池内名次 / 池大小                      # 0~1，池内归一
匹配(item) = ( Σ_{t ∈ tags∩画像tag} w(t)
             + author_boost · Σ_{a ∈ authors∩画像作者} w(a) ) / sqrt(1 + |tags(item)|)
score      = (1 - hot_weight) · 匹配 + hot_weight · 热度
```

- 除以 `sqrt(1 + |tags|)`：不让"标签特别多"的作品白占便宜。
- `author_boost` 默认 1.5：作者是很精准的信号，命中就该明显加分。
- `hot_weight` 默认 0.3：画像弱的时候推出来的还是好东西（顺带就是冷启动兜底）。
- 排序：`score` 降序，同分按热度。

## 5. 冷启动

- 收藏 0 + 搜索 0 → 直接给热度前 N，标题写「热门推荐」（不写"为你推荐"，别骗人）。
- 只有搜索没有收藏 → 也算有画像。
- 候选池里一个 tag / 作者都没命中 → 按热度排（等价于热门）。

## 6. 落点（UI）

- **首页 `#/popular`**：面板里**第一段**（各分类横条之前）「为你推荐」，行头右边「换一批 ›」，下面一行 `--cols` 张卡片（跟分类横条同一套视觉与入场动效）。
- **搜索页 `#/search`**：结果列表**下方**一段；没关键词时也铺在下方。搜索页的推荐把**本次关键词**当一个临时 tag / 作者（权重 1.0，不落库）叠在画像上，所以每次搜索的推荐都不一样（**这条还没得到明确回复，见 §12-3**）。
- 卡片副标题显示"为什么"：`同人 · 中文` / `作者：山田`（`album-card` 的 `subtitle` 现成支持，最多 2 项）。
- **已收藏角标**（用户 2026-10-14 定）：
  - 出现在**所有列作品卡片的地方**：首页 hero 与分类横条、分类页、搜索页、推荐段、论坛的「来自《X》」封面条。
  - **没收藏的卡片一个角标都不加**（不留空位、不加灰标）。
  - 收藏态**不进缓存**：每个列表接口返回前现拼（跟 `_with_covers` 现拼封面一个路子）—— 用户刚收藏完，下一个列表就该是新状态。
  - 角标用收藏那套暖色（`#ff6b81`，跟详情页心形一致），封面右上角，小字「已收藏」+ 心形。
  - **收藏页不打**（整页都是收藏，且卡片角上已经有删除按钮）；详情页保持心形，不加角标。要改的话一句话的事。
- 降级：推荐接口失败 / 超时 → **整段藏起来**，绝不连累页面其他部分。

## 7. 接口（js_api）—— 落地后的形状

```
get_recommendations(kind='home'|'search', limit=None, exclude=[])
    -> {cold: bool, items: [{id, title, cover_url, subtitle, favorited, score}]}
get_taste_profile()
    -> {tags: [{tag, weight}], authors: [{author, weight}], favorites: n, searches: n}
log_search(keyword, scope='site')            # 写 data/app.db 的 search_log
get_search_log(limit=12) -> [{keyword, scope, hits, at}]
remove_search_log(keyword) / clear_search_log()
```

- 返回 `{cold, items}` 而不是裸数组：标题该写「为你推荐」还是「热门推荐」只有后端知道（画像空 / 一个都没命中就是 `cold`），
  不让前端为了换个标题再多问一次 `get_taste_profile`。
- `limit` 不传就用配置里的 `recommend.limit`（0 = 关掉推荐，返回空）；`keyword` 参数**没有**，搜索页一期不吃本次关键词（§12-3）。
- 现有列表接口（`search` / `get_ranking` / `get_forum` / `get_favorites`）返回的作品项统一加 `favorited`（现拼，不进缓存）。
- `get_taste_profile` 一期就做：调试必备，以后设置页能显示"算法记住的 tag / 作者"。

## 8. 搜索记录落库（**已定：方案 A**）

推荐要知道"搜过什么、搜了几次、什么时候搜的"，这些现在只在前端 localStorage（只有关键词，没有次数与时间）。

- 新增 `data/app.db` 表 `search_log(keyword, scope, at)`，接口 `log_search` / `get_search_log` / `remove_search_log` / `clear_search_log`。
- 搜索页的 chips 改读库（单一真相），localStorage 只留榜单 / 范围偏好；`guzhu:search:recent` 那次改造顺手清理掉。
- 理由：项目纪律就是"用户数据放 data/"（收藏就是这么做的）；次数与时间衰减只有后端算得了。

## 9. 配置项（新增 `recommend` 组，按纪律 5 处同步）

```yaml
recommend:
  limit: 10          # 一次铺几张（0 = 关掉推荐）
  candidates: 40     # 候选池大小（热度榜前 N 部，2 页）
  hot_weight: 0.3    # 热度先验占比（0 = 纯画像）
  author_boost: 1.5  # 作者命中相对 tag 命中的倍数
  half_life_days: 30 # 收藏 / 搜索权重的半衰期
```

## 10. 分期

- **一期**：搜索记录落库 + 收藏快照加列 + 收藏态角标（所有列表）+ 画像（收藏 tag / 作者 + 搜索关键词）+ 热度候选池 + 上面的打分 + 首页 / 搜索页两段 + 「换一批」 + `get_taste_profile` + 收藏页预热。
- **二期**：`related_list` 当图上的邻居（"收藏了《X》的人也在看"，字段现成，见 §11）、推荐结果缓存、设置页里显示与调节画像。
- **不做**：隐式反馈（用户 2026-10-14 砍掉）、任何要登录的图源接口。

## 11. related_list 拿得到吗

**拿得到，而且已经在用了**：`get_album_detail` 早就在返回 `related: [{id, title, author, cover_url}]`（A3 那轮加的，取自同一个 `album` 对象，**没有额外请求**），详情页下面那排「相关作品」就是它。
