## 1. Apple 的「hello」是怎么做的，以及网页侧怎么复刻

### 1.1 能核实到的事实

**（1）Apple 没有公开过 hello 动画的技术拆解。** 本次抓取了 Apple Newsroom 2021 年 4 月那篇 24 英寸 iMac 新闻稿全文，检索不到 `hello` 字样，文章只讲硬件与配色；Apple 支持的手册页同样检索不到。Apple 官方设计规范里也没有该动画的实现说明。

- Apple Newsroom：2021 年 24 英寸 iMac 新闻稿（一手）：https://www.apple.com/newsroom/2021/04/imac-features-all-new-design-in-vibrant-colors-m1-chip-and-45k-retina-display/（全文抓取后检索：没有出现 hello 字样 → Apple 未在此文说明该动画）
- Apple 支持：Mac 使用手册・屏幕保护程序（一手）：https://support.apple.com/guide/mac-help/change-the-screen-saver-mchlp1213/mac（本次抓取并检索：正文未命中 hello → 不能拿它当 hello 动画的出处）

**（2）一条需要纠正的「伪一手」来源。** 搜索会命中标题为 `Say hello to the new iMac | Apple` 的 YouTube 视频，看着像 Apple 官方。用 YouTube oEmbed 接口核对作者字段，实际作者是第三方频道 `iFans`，不是 Apple。拿它当一手引用会翻车。

**（3）「Apple hello 用的是描边、遮罩还是别的」——公开资料里没有 Apple 的说法。** 但下面这些公开复刻能反推出社区公认的实现路径：

- GitHub：mtynior/AppleHello（一手仓库，SwiftUI 复刻，MIT）：https://github.com/mtynior/AppleHello（README 自述：Apple 的 Hello 动画用 SwiftUI 复刻；配套讲解属二手博客 thisdevbrain.com）
- GitHub：jrenc2002/AppleCurveAnimation（一手仓库，纯 HTML/CSS 复刻）：https://github.com/jrenc2002/AppleCurveAnimation（README 明确写：用 stroke-dashoffset + stroke-dasharray 加关键帧动画复刻 hello 的曲线动画）
- GitHub：GXeLla/InkTrail（一手仓库）：https://github.com/GXeLla/InkTrail（把任意文字转成「自己写出来」的自包含动画 SVG）

其中 `AppleCurveAnimation` 的 README 写得很直白：它的做法就是给 SVG 路径加 `stroke-dashoffset` / `stroke-dasharray`，再加关键帧动画——也就是业界通称的路径描边（trim path）。`AppleHello` 是同一观感的 SwiftUI 版本（配套讲解博客属二手）。`InkTrail` 则是把任意文字转成自绘 SVG 的现成实现。

> **结论（§1）**：Apple 侧只能拿到观感与设计原则，拿不到实现细节；公开复刻统一走沿笔画路径逐步显现（路径描边），没有看到用遮罩扫过实现 hello 的公开复刻。对只有 5 个字母的字标来说这是好消息——这条路线在 WebView2 里是零依赖的原生能力。

### 1.2 顺带核实的一条 Apple 设计原则（和「开场动画」直接相关）

Apple HIG 的 Launching 章节把话说得很死：启动画面不是一次艺术表达的机会，也不是品牌展示位；并建议启动画面与首屏尽量长得一样，否则会有难看的闪跳；同时给出「用户有时连两秒都不想等」的判断。

- Apple HIG・Launching（一手，Apple 官方设计规范）：https://developer.apple.com/design/human-interface-guidelines/launching（页面为 JS 渲染，正文经 Apple 官方数据接口 developer.apple.com/tutorials/data/design/human-interface-guidelines/launching.json 抓到）

但同一页也承认：splash screen 本身是可以承载品牌的（原文：a beautiful graphic that succinctly communicates branding），前提是别把它和 launch screen 混为一谈。**我们要做的是前者（splash），不是后者（launch screen）**，引用时务必分清。HIG 的 Motion 章节另有两条约束：动效要可跳过 / 可取消，且不要让人为了等动画结束而无法操作。

- Apple HIG・Motion（一手）：https://developer.apple.com/design/human-interface-guidelines/motion（同上，数据接口 .../motion.json）

## 2. 「文字一笔一笔写出来」的实现路线对比

### 2.1 对比表

| 路线 | 观感 | 成本 | 关键 API | Chromium / WebView2 支持 | 主要坑 |
|---|---|---|---|---|---|
| **A. SVG 路径描边**（推荐） | 沿笔画写出来，最接近 hello | 低（一条 path + 一段 CSS） | `stroke-dasharray` / `stroke-dashoffset` + `getTotalLength()` | 两属性均自 **Chrome 1** 起支持 | 笔画路径要自己准备；`dasharray` 需 ≥ 路径总长，否则出现断口 |
| **B. 手写体 + mask / clip 扫过** | 整块推进显形，像镜头擦过 | 低-中（用系统字体则零成本） | `mask-image`（或 `-webkit-mask-image`）/ `clip-path` | 标准 `mask-image` 要 **Chrome / Edge 120+**；`clip-path` 自 **Chrome 55** | 是整行扫过，不是按笔画走；跨平台字体名会碎；系统字体不能随包分发 |
| **C. 变量字体 weight / width 动画** | 字变粗变宽，不是写出来 | 低 | `font-variation-settings` | **Chrome 62+** | 观感对不上需求，只适合字标落位后的微动 |
| **D. Canvas / WebGL** | 想多像就能多像 | 高（自己实现采样、DPR、时序） | Canvas 2D 绘图 API | Canvas 全支持 | 同一套 dash 数学要自己写一遍，收益不抵成本 |
| **E. Lottie** | 效果上限最高（笔触抖动、速度曲线都能做） | 高（要 AE 源文件 + 运行时） | `airbnb/lottie-web` | 取决于运行时与版本 | 引入设计工作流和 ~200KB 级运行时；改字要回 AE |

### 2.2 路线 A（SVG 路径描边）——资源与坑

原理与代码（一手）：`dasharray` 设成「实线段 = 路径全长、间隙 = 路径全长」，再用 `dashoffset` 把实线段推出可视区，动画让 `dashoffset` 归零，就得到画出来的效果；路径全长用 `path.getTotalLength()` 现成拿到。

- Jake Archibald：Animated line drawing in SVG（一手，Chromium 团队成员的技术文章）：https://jakearchibald.com/2013/animated-line-drawing-svg/（给出 getTotalLength() + dasharray/dashoffset 的完整做法与代码）
- MDN：SVGGeometryElement.getTotalLength()（一手文档）：https://developer.mozilla.org/en-US/docs/Web/API/SVGGeometryElement/getTotalLength
- MDN：stroke-dasharray（一手文档）：https://developer.mozilla.org/en-US/docs/Web/CSS/stroke-dasharray
- MDN：stroke-dashoffset（一手文档）：https://developer.mozilla.org/en-US/docs/Web/CSS/stroke-dashoffset
- W3C SVG WG：SVG 2 编辑草案・Painting（一手规范）：https://svgwg.org/svg2-draft/painting.html（含 stroke-dasharray / stroke-dashoffset 定义）

- MDN Browser Compat Data（一手兼容数据，MDN 页面兼容表的数据源）：https://github.com/mdn/browser-compat-data（本次直接读 css/properties/*.json 的 support 字段）

**「笔画路径从哪来」的三种办法**（这才是这条路线的真正工作量所在）：

- **手工画 path**：5 个字母的量级，手画最可控，也最容易做出「一笔写完」的连贯感。上面两个 hello 复刻仓库都是这么来的。
- **单线笔画字体（Hershey）**：Hershey Text 是 Inkscape 里现成的扩展，输出的是单线字形——天生适合描边动画；作者原文注明 Inkscape 0.91 起已内置。
- **普通字体转 SVG path**：后端是 Python，用 fontTools 的 `SVGPathPen` 最顺手；纯前端路线则是 opentype.js。
- Evil Mad Scientist：Hershey Text（一手，单线笔画字体 Inkscape 扩展作者原文）：https://www.evilmadscientist.com/2011/hershey-text-an-inkscape-extension-for-engraving-fonts/（文中注明：Inkscape 0.91 起该扩展已内置（扩展菜单 → Render → Hershey Text））
- fontTools 官方文档：svgPathPen（一手）：https://fonttools.readthedocs.io/en/latest/pens/svgPathPen.html（Python 把字形导出成 SVG path 的官方姿势）
- GitHub：fonttools/fonttools（一手仓库，5.2k star）：https://github.com/fonttools/fonttools
- GitHub：opentypejs/opentype.js（一手仓库，5.0k star）：https://github.com/opentypejs/opentype.js

> **坑（必须知道）**：普通字体转出来的是字形轮廓，一个字常常是多条闭合路径（汉字更是如此，含孔的字母如 `o`、`e` 也是内外两圈）。拿轮廓跑描边动画，会得到先描外圈再描内圈的怪观感，「一笔写完」不成立。**要单线观感，只能手画 path 或用单线笔画字体。**

## 3. 「字标从屏幕中央飞到左上角」怎么做最稳，以及 prefers-reduced-motion 怎么处理

### 3.1 两条路线

**路线一：FLIP（推荐，零依赖）**

FLIP 是 Paul Lewis（Chromium 团队）提出的四步手法，不是库：**F**irst 用 `getBoundingClientRect()` 量出动画前的矩形 → 改 DOM 到最终布局 → **L**ast 再量一次 → **I**nvert 用 `transform` 把元素反推回起始位置 → **P**lay 打开过渡、清掉 transform，让它自己滑到终点。原文给了完整代码（`el.animate([{transform: ...}, {transform: 'translateY(0)'}], ...)`），并强调只动 `transform` / `opacity` 这类合成器友好的属性。

- Aerotwist（Paul Lewis，Chromium 团队）：FLIP Your Animations（一手技术文章）：https://aerotwist.com/blog/flip-your-animations/（First / Last / Invert / Play 四步 + getBoundingClientRect + el.animate() 代码）

对本场景——字标只有一个元素，动的只有位置和尺寸——FLIP 就是最短路径：中央字标量矩形 → 切到左上角导航里的目标样式 → 用同一个元素做 transform 插值。

**路线二：View Transitions（能更省事，但有硬性前提）**

规范与用法见 CSSWG 草案与 MDN 的教程页；Chromium 侧的实操文档在 Chrome for Developers。支持情况：**Chrome / Edge 自 111 起**；跨文档的 `@view-transition { navigation: auto }` 要 **Chrome 126+**。

- W3C CSSWG：CSS View Transitions Level 1（一手规范草案）：https://drafts.csswg.org/css-view-transitions-1/
- MDN：View Transitions API（一手文档）：https://developer.mozilla.org/en-US/docs/Web/API/View_Transitions_API
- MDN：Using the View Transition API（一手文档）：https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using
- Chrome for Developers：Same-document view transitions（一手，Chromium 团队文档）：https://developer.chrome.com/docs/web-platform/view-transitions/same-document
- Chrome for Developers：Cross-document view transitions（一手）：https://developer.chrome.com/docs/web-platform/view-transitions/cross-document
- caniuse：View Transitions（一手兼容数据）：https://caniuse.com/view-transitions（Chrome / Edge 均自 111 起支持）

已知的坑（全部来自上面这些一手文档原文）：

- **名字必须唯一**：同一时刻有两个渲染中的元素带同一个 `view-transition-name`，整个过渡会被直接跳过。
- **一次只能跑一个过渡**：新过渡开始时，旧过渡会被跳到结尾。
- **页面不可见时不跑**：MDN 明确写着，`document.startViewTransition()` 调用期间若文档处于 `hidden`（窗口被遮挡、被最小化、或另一个标签在前），整个过渡会被跳过。
- **跨文档过渡**限同源，且 Chrome 126 阶段仅限主框架导航。
- 过渡默认对 `::view-transition-group` 做 `width` / `height` 插值，会逐帧触发 layout；Chrome 文档自述这块优化尚未实现。

> **和本项目直接相关的一条**：我们的窗口由 pywebview 创建，启动阶段很可能先 `hidden` 再 `window.show()`。按 MDN 那条「不可见即跳过」，启动期用 View Transitions 是不可靠的，而字标飞入恰恰发生在启动期。这就是把 FLIP 放第一位、View Transitions 只当增强的现实理由。

**顺带核实的一条落地前提**（与上面这个可见性坑同源）：pywebview 的 `create_window` 有 `background_color`，官方描述是「WebView 加载完成之前窗口显示的颜色」（默认白色）——即窗口自身底色，不经过 WebView2 渲染。同理 `hidden` 参数与 `window.show()` / `window.events.shown` 是这套流程的控制点。

- pywebview 官方 API 文档（一手）：https://pywebview.flowrl.com/api/（background_color / hidden / window.show() / window.events.*）

### 3.2 prefers-reduced-motion 怎么处理

**规范与兼容**：`prefers-reduced-motion` 定义在 Media Queries Level 5，用来检测用户是否在设备上要求减少非必要动效，取值 `reduce` / `no-preference`。Chromium 侧 **Chrome 74+ / Edge 79+**；caniuse 特别注明这条也取决于操作系统是否暴露该设置。

- W3C CSSWG：Media Queries Level 5（一手规范，prefers-reduced-motion 定义处）：https://drafts.csswg.org/mediaqueries-5/
- MDN：prefers-reduced-motion（一手文档）：https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion
- caniuse：prefers-reduced-motion（一手兼容数据）：https://caniuse.com/prefers-reduced-motion（Chrome 74+ / Edge 79+，并注明「也取决于操作系统是否支持」）

**推荐写法**（MDN 给的形态）：把降级规则写在正常规则之后，同优先级下后者生效即可覆盖；`@media (prefers-reduced-motion)` 等价于 `@media (prefers-reduced-motion: reduce)`。

- MDN：prefers-reduced-motion（一手文档）：https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion
- web.dev：prefers-reduced-motion: Sometimes less movement is more（一手，Google 官方站点文章）：https://web.dev/articles/prefers-reduced-motion

**合规层面要说清的一条**：WCAG 2.3.3（Animation from Interactions，AAA）管的是交互触发的动画，而 WCAG 2.2.2（Pause, Stop, Hide）管的是页面自己发起的动画——开场即播的动画属于后者，方向是能停、能关。

- W3C WCAG 2.3.3 Animation from Interactions 解读（一手；www.w3.org 主站对本机返回 403，正文抓的是 WCAG 工作组官方镜像）：https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html（可读镜像：https://w3c.github.io/wcag21/understanding/animation-from-interactions.html）
- W3C WCAG 2.2.2 Pause, Stop, Hide 解读（一手，WCAG 工作组 GitHub 镜像）：https://w3c.github.io/wcag21/understanding/pause-stop-hide.html

**Windows 侧的设置**：系统确实有「是否允许界面动画」的开关，对应 `UISettings.AnimationsEnabled`。但没有查到 Chromium / WebView2 如何把 Windows 这个开关映射到 `prefers-reduced-motion` 的一手文档，所以不替它做保证，以 CSS 媒体查询的实际生效结果为准。

- Microsoft Learn：UISettings.AnimationsEnabled（一手 API 文档）：https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.animationsenabled（Windows 侧「是否允许界面动画」的系统开关）

**时长上界（能引用的一手数字）**：

- Android 官方对闪屏动画的建议是不超过 1000 ms，并在应用画出第一帧时消隐（同一文档提到启动超过 1000 ms 才考虑循环动画）。
- NN/g 整理的人类工效学三档：0.1 s（感觉是直接操作）、1 s（感觉是自由导航）、10 s（注意力上限）。
- web.dev 的 FCP 阈值：优秀 ≤ 1.8 s，差 > 3.0 s。
- Android Developers：Splash screens（一手官方文档）：https://developer.android.com/develop/ui/views/launch/splash-screen（给出闪屏动画时长建议上界 1000 ms）
- NN/g：Response Times: The 3 Important Limits（一手整理，引人类工效学原始数据）：https://www.nngroup.com/articles/response-times-3-important-limits/（0.1 s / 1 s / 10 s 三档）
- web.dev：First Contentful Paint（一手，Google 官方阈值定义）：https://web.dev/articles/fcp（优秀 ≤ 1.8 s，差 > 3.0 s）

> **结论（§3）**：字标飞入用 FLIP（`getBoundingClientRect` + `transform` + WAAPI），零依赖、与布局系统解耦、启动期也能跑；View Transitions 当可选的增强（先特性探测 `document.startViewTransition` 再决定），不要当必经路径，尤其别在窗口还不可见时用它。`prefers-reduced-motion: reduce` 下直接跳过飞入与描边，改用极短淡入——不是把动画放慢。

## 4. 结论与推荐

**一句话推荐**：开场用 SVG 单线路径 + `stroke-dashoffset` 描边（手画 5 个字母的笔画，约 1.0-1.4 s），动画期间并行预加载；结束时用 FLIP 把同一个字标元素从屏幕中央飞进左上角导航，落位后替代现在的品牌文字。

- **主线（方案 A + FLIP）**：零新依赖，WebView2 兼容性无悬念（`stroke-dashoffset` 自 Chrome 1、`transform` 动画更是基础），失败模式简单，容易做出 hello 那个味道。
- **备选一（View Transitions）**：只在能确认运行环境为 Chromium 111+ 且窗口已可见时启用，用 `if (document.startViewTransition)` 特性探测包一层，探测不到就走 FLIP。
- **备选二（手写体 + mask 扫过）**：想省掉画路径的工作量时才用；观感是擦过而不是写出，且注意标准 `mask-image` 要 Chromium 120+，老 Runtime 走 `-webkit-` 前缀。
- **备选三（Lottie）**：只有愿意引入 AE 设计工作流时才值得，否则杀鸡用牛刀。

**不管选哪条，这三件事必须先确认**（都不是动画本身的问题，但决定看不看得见动画）：

1. 窗口自身底色要和动画底色一致——用 pywebview 的 `background_color`（WebView 加载前就显示的颜色，默认白），否则开场先闪一下白。
2. 窗口可见性：启动期若先 `hidden` 再 `show()`，任何依赖文档可见的过渡都不做。
3. 尊重 `prefers-reduced-motion: reduce`：跳过描边与飞入，保留一个极短淡入。
