## 1. Apple 的「hello」是怎么做的

### 1.1 能核实到的事实

- **Apple 没有公开过 hello 的技术拆解**：2021 年那篇 24 英寸 iMac 新闻稿全文检索不到 `hello`（只讲硬件与配色），
  Apple 支持手册与官方设计规范里也没有实现说明。
- **一条要纠正的「伪一手」来源**：搜索会命中标题像官方的 `Say hello to the new iMac | Apple` 视频，
  用 YouTube oEmbed 核对作者字段，实际是第三方频道 `iFans` —— 拿它当一手引用会翻车。
- **「描边还是遮罩」公开资料里没有 Apple 的说法**，但公开复刻能反推社区公认路径（统一是**路径描边**，
  没见到用 mask 扫过实现的）：
  - `jrenc2002/AppleCurveAnimation`（HTML/CSS 复刻，README 明写用 `stroke-dashoffset` + `stroke-dasharray` + 关键帧）
  - `mtynior/AppleHello`（SwiftUI 复刻，MIT）
  - `GXeLla/InkTrail`（把任意文字转成「自己写出来」的自包含动画 SVG）

> **结论（§1）**：Apple 侧只能拿到观感与设计原则，拿不到实现细节；对只有 5 个字母的字标来说是好消息 ——
> 这条路线在 WebView2 里是零依赖的原生能力。

### 1.2 顺带核实的一条 Apple 设计原则（和开场动画直接相关）

Apple HIG 的 Launching 章节把话说得很死：启动画面**不是**一次艺术表达的机会、也不是品牌展示位，并建议启动画面与首屏
尽量长得一样（否则会有难看的闪跳），还给出「用户有时连两秒都不想等」的判断。但同一页也承认 **splash screen 本身
可以承载品牌**（原话：a beautiful graphic that succinctly communicates branding）—— 前提是别把它和 launch screen
混为一谈。**我们要做的是前者（splash），不是后者。** HIG 的 Motion 章节另有两条约束：动效要可跳过 / 可取消，
且不要让人为了等动画结束而无法操作。

## 2. 「文字一笔一笔写出来」的实现路线对比

### 2.1 对比表

| 路线 | 观感 | 成本 | 关键 API | Chromium / WebView2 支持 | 主要坑 |
|---|---|---|---|---|---|
| **A. SVG 路径描边**（推荐） | 沿笔画写出来，最接近 hello | 低（一条 path + 一段 CSS） | `stroke-dasharray` / `stroke-dashoffset` + `getTotalLength()` | 两属性均自 **Chrome 1** 起支持 | 笔画路径要自己准备；`dasharray` 需 ≥ 路径总长，否则出现断口 |
| **B. 手写体 + mask / clip 扫过** | 整块推进显形，像镜头擦过 | 低-中（用系统字体则零成本） | `mask-image`（或 `-webkit-mask-image`）/ `clip-path` | 标准 `mask-image` 要 **Chrome / Edge 120+**；`clip-path` 自 **Chrome 55** | 是整行扫过，不是按笔画走；跨平台字体名会碎；系统字体不能随包分发 |
| **C. 变量字体 weight / width 动画** | 字变粗变宽，不是写出来 | 低 | `font-variation-settings` | **Chrome 62+** | 观感对不上需求，只适合字标落位后的微动 |
| **D. Canvas / WebGL** | 想多像就能多像 | 高（自己实现采样、DPR、时序） | Canvas 2D 绘图 API | Canvas 全支持 | 同一套 dash 数学要自己写一遍，收益不抵成本 |
| **E. Lottie** | 效果上限最高（笔触抖动、速度曲线都能做） | 高（要 AE 源文件 + 运行时） | `airbnb/lottie-web` | 取决于运行时与版本 | 引入设计工作流和 ~200KB 级运行时；改字要回 AE |

### 2.2 路线 A（SVG 路径描边）——原理、资源、坑

- **原理**：`dasharray` 设成「实线段 = 路径全长、间隙 = 路径全长」，再用 `dashoffset` 把实线段推出可视区，
  动画让 `dashoffset` 归零就是「画出来」；路径全长用 `path.getTotalLength()` 现成拿到。
  `stroke-dasharray` / `stroke-dashoffset` 在 Chromium 侧**自 Chrome 1 起支持** → WebView2 上无风险。
- **现成库**：`maxwellito/vivus`（15.5k star，**2022-07 起停更，注意风险**）、
  `rveciana/svg-path-properties`（getTotalLength 之外的纯 JS 替代）。
- **「笔画路径从哪来」——这才是这条路线的真正工作量**：
  ① **手画 path**：5 个字母的量级，最可控、最容易做出「一笔写完」的连贯感（两个 hello 复刻仓库都是这么来的）；
  ② **单线笔画字体 Hershey**：Inkscape 的 Hershey Text 扩展（0.91 起内置），输出单线字形，天生适合描边动画；
  ③ **普通字体转 SVG path**：后端是 Python，用 fontTools 的 `SVGPathPen` 最顺手；纯前端则用 opentype.js。
- **坑（必须知道）**：普通字体转出来的是**字形轮廓** —— 一个字常是多条闭合路径（汉字如此，含孔的 `o` / `e` 也是内外两圈），
  拿它跑描边会得到「先描外圈再描内圈」的怪观感，「一笔写完」不成立。
  **要单线观感，只能手画 path 或用单线笔画字体。**

### 2.3 路线 B（手写体 + mask 扫过）——为什么没选

- **Windows 自带手写风字体的实况**（逐条在 Microsoft 官方字体清单里查过）：Ink Free / Segoe Script / Gabriola
  在 Win10 与 Win11 清单里都有；Segoe Print 只在 Win10 清单里查到（Win11 那份只核了三条）。
- **没查实、别依赖**：`Lucida Handwriting` / `Brush Script MT` / `Mistral` / `Freestyle Script` 在两份官方清单里
  均无命中 —— 网上教程常推荐，但不能当「Windows 自带」。
- **授权口径**：用 Windows 自带字体做打印 / 图形输出基本不设限制，但这类字体**随 Windows 安装，不能把字体文件
  打进安装包分发**。想随包分发、保证跨环境一致，就换 OFL 授权的开源手写体（Caveat / Dancing Script / Great Vibes）。
- **兼容与观感**：标准 `mask-image` 要 **Chrome / Edge 120+**（老 WebView2 得靠 `-webkit-mask-image` 兜底），
  `clip-path` 自 Chrome 55。更要紧的是**观感是本质差异**：mask / clip 是一条边界推过去（像镜头擦过纸面），
  不是笔尖沿笔画走 —— 想要 hello 那个味道只有路线 A。

### 2.4 路线 C / D / E 的定位

变量字体动画（`font-variation-settings`，Chrome 62+）能把字长胖长高，是很好的**落位微动**，但做不出「写出来」；
Canvas 相当于把路线 A 的数学自己实现一遍（除非要做笔尖压感 / 抖动，否则不划算）；Lottie 效果上限最高，
但要把 AE 工作流引进来，字标改一个字都要回炉。

## 3. 「字标从中央飞到左上角」怎么最稳，以及 prefers-reduced-motion 怎么处理

### 3.1 两条路线

**路线一：FLIP（推荐，零依赖）** —— Paul Lewis（Chromium 团队）提的四步手法，不是库：
**F**irst 用 `getBoundingClientRect()` 量出动画前的矩形 → 改 DOM 到最终布局 → **L**ast 再量一次 →
**I**nvert 用 `transform` 把元素反推回起始位置 → **P**lay 打开过渡、清掉 transform 让它自己滑到终点。
只动 `transform` / `opacity` 这类合成器友好的属性。本场景只有一个元素、只动位置与尺寸 → 这就是最短路径。

**路线二：View Transitions（更省事，但有硬性前提）** —— 支持：**Chrome / Edge 111+**，跨文档的
`@view-transition { navigation: auto }` 要 **126+**。已知的坑（全部来自一手文档原文）：

- **名字必须唯一**：同一时刻两个渲染中的元素带同一个 `view-transition-name`，整个过渡被**直接跳过**。
- **一次只能跑一个过渡**：新过渡开始时旧过渡会被跳到结尾。
- **页面不可见时不跑**：`document.startViewTransition()` 调用期间若文档处于 `hidden`（被遮挡 / 最小化 / 别的标签在前），
  整个过渡被跳过。
- 跨文档过渡限同源，且 Chrome 126 阶段仅限主框架导航；默认对 `::view-transition-group` 做 `width` / `height` 插值，逐帧触发 layout。

> **和本项目直接相关的一条**：窗口由 pywebview 创建，启动阶段很可能先 `hidden` 再 `window.show()`；
> 而字标飞入恰恰发生在启动期 → **启动期用 View Transitions 不可靠**。这就是把 FLIP 放第一位、
> View Transitions 只当增强的现实理由。

**顺带核实的一条落地前提**：pywebview 的 `create_window` 有 `background_color`，官方描述是「WebView 加载完成之前
窗口显示的颜色」（默认白，这就是「开场先闪一下白」的来源）；`hidden` 参数与 `window.show()` / `window.events.*`
是这套流程的控制点。

### 3.2 prefers-reduced-motion 怎么处理

- **写法**（MDN 给的形态）：把降级规则写在正常规则**之后**，同优先级下后者生效即可覆盖；
  `@media (prefers-reduced-motion)` 等价于 `@media (prefers-reduced-motion: reduce)`。
  兼容：Chrome 74+ / Edge 79+，caniuse 注明**还取决于操作系统是否支持**。
- **合规口径**：**开场即播**的动画归 WCAG **2.2.2（Pause, Stop, Hide）**管，方向是「能停、能关」；
  WCAG 2.3.3（Animation from Interactions，AAA）管的是**交互触发**的动画 —— 引用时别弄混。
- **时长上界（能引用的一手数字）**：Android 官方建议闪屏动画**不超过 1000 ms** 并在画出第一帧时消隐；
  NN/g 的人类工效学三档 0.1 s（直接操作感）/ 1 s（自由导航感）/ 10 s（注意力上限）；web.dev 的 FCP 阈值
  优秀 ≤ 1.8 s、差 > 3.0 s。
- **Windows 侧**确实有「是否允许界面动画」的系统开关（`UISettings.AnimationsEnabled`），但**没查到**
  Chromium / WebView2 如何把它映射到 `prefers-reduced-motion` 的一手文档 → 不替它做保证，以实际生效结果为准。
- **结论**：`reduce` 下**直接跳过飞入与描边、改用极短淡入** —— 不是把动画放慢。

## 4. 结论与推荐

**一句话推荐**：开场用 SVG 单线路径 + `stroke-dashoffset` 描边（手画 5 个字母的笔画，约 1.0-1.4 s），动画期间并行预加载；结束时用 FLIP 把同一个字标元素从屏幕中央飞进左上角导航，落位后替代现在的品牌文字。

- **主线（方案 A + FLIP）**：零新依赖，WebView2 兼容性无悬念（`stroke-dashoffset` 自 Chrome 1、`transform` 动画更是基础），失败模式简单，容易做出 hello 那个味道。
- **备选一（View Transitions）**：只在能确认运行环境为 Chromium 111+ 且窗口已可见时启用，用 `if (document.startViewTransition)` 特性探测包一层，探测不到就走 FLIP。
- **备选二（手写体 + mask 扫过）**：想省掉画路径的工作量时才用；观感是擦过而不是写出，且注意标准 `mask-image` 要 Chromium 120+，老 Runtime 走 `-webkit-` 前缀。
- **备选三（Lottie）**：只有愿意引入 AE 设计工作流时才值得，否则杀鸡用牛刀。

**不管选哪条，这三件事必须先确认**（都不是动画本身的问题，但决定看不看得见动画）：

1. 窗口自身底色要和动画底色一致——用 pywebview 的 `background_color`（WebView 加载前就显示的颜色，默认白），否则开场先闪一下白。
2. 窗口可见性：启动期若先 `hidden` 再 `show()`，任何依赖文档可见的过渡都不做。
3. 尊重 `prefers-reduced-motion: reduce`：跳过描边与飞入，保留一个极短淡入。
