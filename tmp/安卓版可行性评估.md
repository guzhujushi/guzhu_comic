## 0. 一句话结论

1. **技术上能上，但绝不是「重新打个包」的活。** 桌面跑起来的那几层壳（pywebview / PyInstaller / WebView2 / DWM 亚克力 / 注册表 / 托盘）在安卓上全部作废，`main.py` 整个入口要重写。**但业务层可以基本原样复用** —— `backend/api.py` 2441 行、前端 31 个 `.ts`，一行业务逻辑都不用改。这是这个项目上安卓最大的本钱。
2. **真正的死穴已经不是网络层了。** 图源要 Chrome TLS 指纹（`curl_cffi`；§0.5 实测「普通 urllib 直连会 TLS reset」），而 **`curl_cffi` 0.16.3 已发官方 `android_24_arm64_v8a` wheel（cp313 / cp314）**（**已核实**：PyPI 文件列表），Chaquopy 17.x 吃的正是这个 tag。也就是说「Python 端上跑」这条路 2026-10 是通的（**待实测**）。放在两三年前，这是一条死路。
3. **卡脖子的三件事换成了**：① **Android 生命周期**（全项目建立在「窗口在 = 进程活」上）；② **桥**（`window.pywebview.api.*` 在安卓 WebView 上不存在，54 个方法要另找通道）；③ **触屏 UI**（大量交互靠鼠标悬停与键盘，手机上够不着）。外加**合规**（Play 上不了架、国内 APP 备案）这条非技术风险。

## 1. 现状盘点：哪些已经是「上安卓的底子」

| 资产 | 为什么值钱 | 出处 |
|---|---|---|
| 前端是**纯静态 dist**、手写 hash 路由、原生 DOM、无框架无 SSR | 直接塞进 Android WebView 就能跑，不需要重写 UI 层 | `frontend/dist`、`router.ts` |
| 打包态就是**一个本地 HTTP 服务喂 dist、页面与图同源** | 安卓上照搬，只需多挂一层 `/api`（见 §3-D2） | `backend/server.py` |
| **`backend/paths.py` 是数据 / 资源路径的唯一入口** | 文件开头注释写的就是「Android 上换成 app 私有目录」；改一处 | `backend/paths.py:1-40` |

| 业务代码里**没有** `sys.platform` / `sys.frozen` | 打包分发设计 §9 定的三条边界基本守住了 | `paths.py` 注释、`glass.py:37` |

## 3. 难点（按「会不会卡死项目」排序）

### D1 Android 生命周期 —— 最难，而且是设计层面的（不是改代码）

- **现状**：`main.py` 开窗 → `webview.start()` 阻塞到关窗 → 进程退出；下载线程是 daemon；进度在「关窗那一刻」落库（`desktop.watch_geometry` 的 `on_closing`、阅读器的三条退出路径）；缓存清理是后台 `_cache_loop` 线程。
- **安卓上没有「关窗」这个事件**。Activity 会被销毁、进程随时可能被杀（Doze、内存回收、国产 ROM 的省电策略）。**没有 `closing` 钩子 = 没有「退出前把进度写下去」的时机** → 必须改成：`onPause`/`onStop` 时 `evaluateJavascript` 主动让前端落一次进度，或者前端把 `save_progress` 改成节流 + 定时写库。
- **后台下载要靠前台服务**：一话 200 张图、整本几百 MB（README 里「整本已离线（12 话 · 320 MB）」）。桌面上「关窗只是暂停一下」，手机上不保活就是「切出去 30 秒后被冻结」。需要 `startForegroundService` + 常驻通知 + `WAKE_LOCK`，Android 13+ 还要 `POST_NOTIFICATIONS` 运行时权限。
- **加分项**：现有下载器「进度以磁盘为准、重启只补缺的」这套设计，正好是手机被杀的兜底 —— 这块的设计是提前做对了的。

### D2 桥（js_api → Android WebView）

- **好消息**：桥是单向的（无 `evaluate_js`），所以不需要回调通道（**已核**）。
- **三个可选实现**：
  - **(a) `addJavascriptInterface`**：Java 对象注入 + 转 `PyObject.callAttr`。每次调用跨 JS→Java→Python 三层，大 JSON（一话 200 个 URL）要序列化两次；`@JavascriptInterface` 方法跑在非 UI 线程，返回只能同步或回调。
  - **(b) 本地 HTTP JSON-RPC（推荐）**：`backend/server.py` 已在跑静态服务，加 `POST /api/<method>` 即可；前端写一个几十行的垫片把 `window.pywebview` 造出来（`api` 对象 + 派发一次 `pywebviewready`），**51 处 `window.pywebview` 引用一行都不用改**。
  - (c) pywebview 官方 android 后端：见 R3，不要。
- **垫片与现有自愈逻辑的关系**：前端有 `waitForBridge(quietMs=800)` + `bridgeCall` 重注入重试那一整套（防 pywebview 两步注入），垫片是同步挂好的，那套会立刻通过 —— 留着无害，但别指望它兜 HTTP 错误。
- **顺手要补的安全洞**：本地 47753 在安卓上**同设备的任意 app 都能访问**（不像桌面还有 Host 白名单挡一层）。→ 启动时生成随机 token，`/api` 校验；桌面版本同样受益。这是本评估里唯一一条「顺便就把洞补了」的项。

### D3 依赖落地与体积

- 见 §2 那张表：**关键变量是 curl_cffi**，其余都有 wheel 或纯 Python。
- **体积**：arm64 单 ABI 的 APK，估计 **40~60 MB**（主要块是 curl_cffi 的 22.9 MB `.so` + Python 运行时 ~12.6 MB，未实测）（Python 运行时 + Pillow + pycryptodome + curl_cffi 自带的 libcurl-impersonate）。对比桌面 zip 20 MB —— 手机用户能接受，但要有预期（**未实测**，§6-T4）。
- **版本要看住**：Chaquopy 仓库里的 `Pillow` 是 11.0（cp313），jmcomic 对 Pillow 的版本要求要先核对；`curl_cffi` 的 android wheel 只有 cp313/cp314 —— 选 Python 版本时 **3.13 比 3.15 稳**（两个依赖都覆盖）。

### D4 路径 / 存储 / 权限

- `APP_DIR = Path.home() / ".jmreader"`（`backend/paths.py:19`）在安卓上**不可控**（`Path.home()` 在 Chaquopy 下指向哪不能猜）→ 必须显式注入 `context.getFilesDir()`。**这是一层设计时就留好的口子，改一处。**
- 但三块语义要在安卓上拆开：
  - `config` + `data`（sqlite）→ app 私有目录（卸载即清）；
  - `cache` → `getCacheDir()`：**系统空间紧张时会被系统自己删**（比现在「按 2 GB 上限清理」更狠，但语义上其实更对）；
  - **离线下载（用户数据，几十~几百 MB，不能被系统清）** → `getExternalFilesDir()` 或用户选的 SAF 目录。
- **默认值要分平台**：`cache.max_size_mb = 2048` 在手机上是荒唐值（很多手机可用空间就 3~5 GB）→ 512~1024；`download.workers = 8` → 2~3（手机网络 + CPU）；`splash.min_ms = 1950` 在手机上偏长。
- **权限**：Android 11+ 分区存储。私有目录外一律走 SAF（`ACTION_OPEN_DOCUMENT_TREE` / `CREATE_DOCUMENT`），不能直接按路径 `open()`。受影响接口：`export_data` / `import_data` / `create_file_dialog`（`api.py:2414`，现在直接 `import webview`）/ `open_folder`（现在 `subprocess.Popen(["explorer", ...])`）。
- 附带一个坑：`shutil.disk_usage`（`api.py:2017`）在安卓上读到的是 root 分区，要换 `StatFs`。

### D5 长图渲染与内存 —— 手机上必炸，桌面也该改

- `reader.ts` 的 `renderImages()` **一次性把整话所有 `<img>` 建出来并立刻赋 `src`**（无 lazy）。实测一话 207 张（STATUS「直连实测」）。桌面上「图都在本地、随便」；手机上 207 个并发图片请求 + 解码 = 内存爆掉（一张 1000×2000 解码后就是 8 MB 量级）。
- **要改**：`loading="lazy"` 或 IntersectionObserver 懒加载，前后各留 2~3 张。**这条桌面也受益**（首屏更快、内存更低），属于「安卓需求反哺桌面」的典型。
- **更硬的一层**：JM 的条漫长图常是 1000×20000 这种极端比例，Android WebView 在硬件加速下受纹理尺寸上限约束（设备相关，常见 4096/8192/16384），超限会整张不显示或掉到软件绘制。对策是后端按高度切块（Pillow 现成）。**必须先实测**（§6-T3）。

### D6 触屏交互与布局 —— 前端改动量最大的一块

- **布局**：`--rail: 208px` 固定左栏（`style.css:32`）。手机宽 360~430 dp → 必须变底部 Tab 或抽屉；现有 `@media (max-width: 1180px)` 只把 rail 收到 64px，手机上 64px 也是纯浪费。改动集中在 `style.css`（69 KB）+ `main.ts` 的导航渲染。
- **hover 显形的操作在触屏上完全不可达**（49 处 `:hover`，其中这几处是「不悬停就点不到」）：章节行右边的「只下这一话」（`.chapter-dl` 靠 `.chapter-row:hover` 显形）、卡片右上角删除（`.card-del` 靠 `album-card:hover`）、hero 的 `mouseenter` 轮播。要改成常驻或长按菜单。
- **键盘全废**：`/` 进搜索、`Esc` 关浮层、`←/→/空格/Home/End/M`（阅读器）。阅读器工具条现在是**按 `mousemove` 分上下唤出**（2026-10-14 刚做的三项体验之一）—— 触摸屏没有 mousemove，要换成「点上半屏 / 下半屏」或上滑下滑。
- **返回键**：Android 物理返回 / 手势返回默认不会映射到历史后退，要在 Java 侧拦 `onBackPressed` 调 `webView.goBack()`；前端现有的 `popstate` + `history.state.__seq` 那套（返回还原）要在这条链路上重新验。
- **安全区**：`viewport-fit=cover` + `env(safe-area-inset-*)`，主要影响阅读器顶栏底栏与底部导航。
- **`100vh`**：安卓地址栏收缩会跳（`min-height: 100vh` 用了 3 处）→ `dvh`/`svh`（低版本 WebView 要留回退）。
- 还要收口：下拉刷新 / 误触、长按选中文本、双击缩放。
- **好消息**：CSS 用的都是保守特性（`aspect-ratio` / `backdrop-filter` / `clip-path`），**没有** `:has` / `@container` / `oklch` 这些「新内核才有」的东西 —— Android WebView 可独立升级，兼容性风险低。

### D7 系统集成（`backend/desktop.py` 512 行整块作废）

| 桌面能力 | 安卓对应 | 说明 |
|---|---|---|
| 托盘图标 | 无 | 删；设置项按平台隐藏 |
| 开机自启（winreg） | `BOOT_COMPLETED`（可选） | 一般不给这类 App 做 |
| 全局快捷键（ctypes 消息循环） | 无 | 删 |
| 窗口几何记忆 | 不需要 | 删 |
| 系统通知 | `NotificationChannel` + 前台服务 | **升级为下载保活的必需品**（D1） |
| `open_folder` | SAF / 系统文件 App | 语义变了（`explorer` → `Intent`） |
| `create_file_dialog` | SAF | `api.py:2414` |

**做法**：按打包分发设计 §9 定的边界，把这块挪进 `backend/platform/` 门面（`desktop_windows.py` / `desktop_android.py`），业务代码继续只认门面。`settings_spec.py` 的表是**声明式**的（前端表单由它生成）→ 给字段加一个 `platform` 属性就能自动隐藏不适用项，成本很低。

### D8 热更新与版本

- 机制可原样保留（写 app 私有目录 + 每请求挑根，不需要任何安卓特权）。
- 但 `updater` 的 `app_min` 校验的是壳版本（`backend/version.py` 的 `APP_VERSION`），安卓上必须与 `versionName` / `versionCode` 对齐，否则会出现「热更要求 0.2.0，壳自称 0.1.1」。
- **合规**：Google Play 明文禁止运行时下载并加载可执行代码（WebView 里的 HTML/JS 算擦边）。既然这个 App 本来就上不了 Play（内容原因），这条不是主要障碍 —— 但「别指望上架商店」要写进文档。

### D9 构建与调试

- 桌面现在是 `PyInstaller onedir + PowerShell + 32 秒出包`。安卓变成 `Gradle + Android SDK/NDK + Chaquopy 插件`：**第一次把构建链跑通本身就是一两天**（SDK/NDK 十几个 GB、JDK/AGP/Gradle 版本搭配）。Windows 上可行（Chaquopy 支持 Windows 构建），但调试从「双击 `main.py` 看窗口」变成 `adb logcat` + 重装 APK，迭代速度差一个量级。
- 产物就是 APK 侧载（不上商店不用 AAB）。

### D10 合规与分发 —— 唯一一条「技术全通也上不了」的障碍

- **Google Play 上不了**：成人内容违反 Play 政策。
- **国内 APP 备案**：2023 年起在国内分发的 App（含 APK 直接分发）需备案；没备案商店上不了，侧载是灰色地带。
- 内容定性：桌面用户「自己下 exe」与「应用商店里的一个 App」性质不同，分发形态会放大风险。
- **结论**：动手前先把分发方式想清楚（同学间侧载 APK？自建更新通道？），否则技术做完了也没法发。

## 5. 建议路线与工作量

1. **P0（不用安卓机器、1~2 人天）：把桥换成 HTTP JSON-RPC。** `server.py` 加 `/api` + token，前端加垫片，**桌面一起切过去**。立刻拿到三样东西：① 手机浏览器直接访问 PC 的 47753 就能用 → **不写一行安卓代码就能验证「这套 UI 在手机上到底多难用」**，还顺带成立 R1（瘦客户端）；② 桌面也能在浏览器里调试前端（省掉 pywebview 那套注入时序的坑）；③ 任意后续路线的第一步。

## 7. 结论

- **要「手机上也能看」**：先做 P0（1~2 人天，桌面也受益），再决定 R1 还是 R2 —— P0 之后手机浏览器就能试，UI 好不好用当场见分晓。
- **要「做一个安卓 App」**：走 **R2（Chaquopy + AndroidX WebView + 本地 HTTP）**，别走 R3（p4a+Kivy，白背一套 UI 栈）、别走 R4（Kotlin 重写，TLS 指纹自己拼 BoringSSL 不值得）。
- **最大风险不在技术**：内容是 D10 那条 —— Play 上不了架、国内要备案。**这个问题没想清楚之前，不建议投入 R2 的工作量。**
- **一句话**：安卓上「能不能看」的关键早就不是 Python，而是 `curl_cffi`（Chrome 指纹）；而这一条在 2026-10 从「死路」变成了「有官方 wheel」。剩下的是三件事：生命周期、桥、触屏 UI。
- **2026-10-15 晚补**：上面这句话的**前提已经实测坐实** —— 在真跑起来的安卓运行时（arm64 包 + 模拟器翻译层）里，`curl_cffi` 装得上、TLS 指纹通、图源接口全通（T1 / T1-b / T2 关闭，`tmp/安卓依赖探针实测.md`）。**所以对「技术上能不能上安卓」这个问题，本次评估的答案从「大概率能」变成「能」。**
  剩下的真机项只有 T3~T6（手感 / 内存 / 保活），**它们不阻塞开发**；真正该先解决的仍然是 **P0（带 token 的本地 HTTP 桥）** 与 **D10（分发合规）**。
