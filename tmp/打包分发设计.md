## 1. 现状：为什么"`npm run build` 完了也打不出能用的包"

四个卡点，全都有据可查：

| # | 卡点 | 证据 |
|---|---|---|
| 1 | `main.py` 只吃 `dev.url`，压根没有"加载本地 dist"这条路 | `main.py:18`（`url=dev_cfg["url"]`）、`tmp/交接文档.md` §5.19 |
| 2 | 配置文件路径钉在源码位置上，冻结后会跑进 `_internal/` | `backend/config.py:8`（`Path(__file__).resolve().parent.parent / "config.yaml"`） |
| 3 | 没有静态服务，`dist` 没地方挂 | 全仓库没有 dist 相关代码；`backend/api.py:867` 那个 HTTP 服务只服务图片 |
| 4 | pywebview 默认 `private_mode=True`，WebView2 的 user data 落在**临时目录**，每次开窗清空 | `webview/platforms/winforms.py:743-757`：`private_mode` 且无 `storage_path` → `tempfile.TemporaryDirectory().name` |

## 5. 端口：为什么是 47753

**选型依据**（三条都实测过）：

1. **> 4096**：普通用户进程就能绑，不需要管理员。
2. **< 49152**：Windows 的**动态端口段**是 `49152 + 16384`（本机实测：`netsh int ipv4 show dynamicport tcp` → Start 49152 / 16384）。这个段是给出站连接随机分配的 —— 如果服务绑在 49152 以上，本进程（curl_cffi 那一堆请求）的出站连接可能先随机占到它，导致某次启动"端口被占"。
3. **不在保留段**：本机 `netsh interface ipv4 show excludedportrange protocol=tcp` 只有 `5357`（WSDAPI），47753 不在里面。

**实测**：10 个候选全部空闲（47753 / 47823 / 47123 / 41999 / 45711 / 47251 / 49151 / 49321 / 51080）；最终选 **47753**。

**回退策略**：47753 → 47754 … 47760 依次试；全被占就退回 `0`（系统随机）。

⚠️ 回退的副作用要说清楚：**origin 一变，WebView2 的 `localStorage` 就是另一个 origin**，用户会觉得"主题/偏好被重置了"。所以：首选固定端口，回退时**建议在日志里记一笔**（将来如果不想要这个副作用，就得把主题/偏好搬到后端 `config.yaml`，但那会让首帧主题闪一下 —— 现在 `index.html` 里那段内联脚本靠的就是 localStorage，别改）。

**图片服务**：按 §4 合并进同一个端口后，`img_base` 就等于页面 origin，跨源问题一起消失。

## 6. 怎么构建

脚本：`scripts/build_exe.ps1`（**实测可跑通**，产物 39 MB / zip 19.9 MB / 约 25 秒）。

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-build.txt   # pyinstaller>=6.22（实测 6.22.3）
powershell -ExecutionPolicy Bypass -File scripts\build_exe.ps1
```

脚本做的事：`npm run build`（可 `-SkipFrontend` 跳）→ Pillow 生成 `app.ico` → 写 version-file → PyInstaller → 体积报告 → zip。

PyInstaller 参数逐条为什么：

| 参数 | 为什么 |
|---|---|
| `--onedir`（**不是 `--onefile`**） | onefile 每次启动解压自身到 `%TEMP%`，是杀软行为引擎的头号嫌疑；onedir 启动也更快 |
| `--noupx` | UPX 壳会让启发式引擎加权重；省下那点体积不值得 |
| `--windowed` | 发布态不留控制台；**实测 windowed 与 console 行为一致**（页面照样起来、桥照样通） |
| `--icon` / `--version-file` | exe 图标 + 文件属性；"没有版本信息的 PyInstaller exe" 是误报的常见画像 |
| `--add-data "frontend/dist;dist"` | 前端产物 → `<exe>/_internal/dist`（Windows 下分隔符必须是 `;`） |
| `--collect-all webview pythonnet clr_loader curl_cffi jmcomic` | 这几个包的运行时依赖收不全：webview 的 WebView2 DLL / js、pythonnet 的 `Python.Runtime.dll`、clr_loader 的 `ClrLoader.dll`、curl_cffi 的 `libcurl-impersonate`、jmcomic 的动态插件扫描 |
| `--hidden-import clr` | pywebview 的 Windows 后端 `import clr` 是间接的，静态分析常常扫不到 |
| `--exclude-module tkinter / PIL.AvifImagePlugin / test / unittest / pydoc` | 实测砍 15.5 MB（54.4 → 38.9），且功能无回归 |

**两个坑**：

- **`.ps1` 必须存成 UTF-8 带 BOM。** PowerShell 5.1 把无 BOM 的脚本按 ANSI（本机 GBK）读，中文注释会直接把语法解析搞坏（实测：无 BOM → 6 处语法错误；加 BOM → 通过）。这条与 `AGENTS.md` 里"脚本用 UTF-8 无 BOM"的口径冲突 —— 那条是针对 sh/`.py` 的，**`.ps1` 例外**。
- **PowerShell 的 `&` 不会等 GUI（windowed）子系统的 exe**：`& .\GuzhuComic.exe` 立刻返回，看着像"没跑起来"。要等就用 `Start-Process -Wait`，或者轮询进程/产物文件。

## 7. 优先级 1：拿到文件和可执行程序就能用

**交付形态**：`GuzhuComic-0.1.0-win64.zip`（19.9 MB）→ 解压 → 双击 `GuzhuComic.exe`。无安装、无管理员权限、不写注册表、不写 `Program Files`。

**运行时依赖矩阵**（实测本机值）：

| 依赖 | 谁要 | Win11 | Win10 1803+ | 怎么判 |
|---|---|---|---|---|
| WebView2 Runtime | 唯一真正的外部依赖 | 自带 | 多数自带（随 Edge） | 注册表 `…\EdgeUpdate\Clients\{F3017226-…}` 的 `pv`（本机 155.0.4283.45） |
| .NET Framework 4.6.2+ | pythonnet 默认走 **netfx**（`pythonnet.set_runtime_from_env` 在 Windows 上默认 legacy .NET Framework），所以只要 4.x | 自带 | 自带 | `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full` 的 `Release`（本机 4.8.09221 / 533509） |
| VC++ 运行库 | `python314.dll` | 由 PyInstaller 带 `vcruntime140*.dll` | 同 | 包内已有（实测） |
| Node / Vite / Python / pip | **不需要** | — | — | 只在构建机 |

**数据落在哪**（用户目录，可整目录拷走迁移）：`~/.jmreader/{config.yaml, data/app.db, cache/, downloads/, webview/, logs/}`。

**首启体验**：`~/.jmreader` 不存在就自动建；`config.yaml` 不存在就写一份默认值。装完即用，不需要任何命令行。

## 8. 优先级 2：把杀软误报压到最低

误报**不能归零**（未签名的新 exe + 联网抓图 + 多线程下载 + 写用户目录，本身就是行为引擎的兴趣点），只能压低 + 留申诉通道。

**已经做到的**（都在 `scripts/build_exe.ps1` 里）：`--onedir`（不自解压、不往 `%TEMP%` 丢东西）、`--noupx`（不加壳不压缩）、
exe 带图标 + 完整版本信息、用官方 CPython、**不写系统目录 / 不写注册表 / 不改 hosts / 不注入别的进程**
（数据全在 `~/.jmreader`，卸载 = 删目录）、分发成 **zip**（而不是裸 exe 直链）。

**实测**：Defender（引擎 4.18.26090.9）扫 onedir / exe / zip 三处全 `found no threats`；
**VirusTotal 75 引擎**（2026-10-14，脚本 `tmp/_vt_scan.py`，key 走环境变量，**上传即把样本共享给厂商**，已与用户确认）：
发出去的 zip **0/75**，裸 exe **3/75** —— 三家都是**行为启发式**（`APEX`、`Skyhigh: BehavesLike...`（McAfee 系，
`BehavesLike` 前缀 = 启发式而非特征命中，PyInstaller 程序是常客）、`Zillya: Trojan.Blank.Script.*`（乌克兰小厂，
名字带 Script 而样本是 PE）。**主流大厂与国内杀软全放行**（Microsoft / Kaspersky / ESET / BitDefender / Avast / Symantec /
Sophos / CrowdStrike …，以及火绒 / 腾讯 / 金山 / 瑞星 / 阿里 / 安天 / 江民 / 深信服）。逐引擎报告在 `tmp/_vt/`。

**2026-10-15 复扫 0.1.2**（跑法同前，样本仍上传给厂商）：裸 exe **3/75**（`APEX`、`Cylance: Unsafe`、
`Skyhigh: BehavesLike.Win64.Backdoor.vc`），发出去的 zip **1/75**（`Zillya: Trojan.Blank.Script.2228` ——
跟上一版同一个乌克兰小厂、同一个 `Script` 启发式，而样本其实是 PE）。两次扫出来的都不是特征命中；
`tmp/_vt/` 里两份 JSON 就是证据（`GuzhuComic.exe.json` / `GuzhuComic-0.1.2-win64.zip.json`）。

**还没做的**：① **代码签名**（唯一能根治 SmartScreen「未知发布者」与多数启发式扣分的办法；要花钱，**待用户决定**，
不做就把首次运行提示写进 README）；② 为那两家提误报申诉（用户定，还没提）；
③ 本机的 **360 / 火绒 / 腾讯客户端**仍然没装、没测（VT 上这三家引擎放行 ≠ 本地客户端不拦，特征库不同）。

**发布纪律**：同一构建机、同一 Python 小版本、同一套 flags，别每次换环境重打（哈希一变就可能重新触发未知文件判定）。
**别做**：不要试图混淆 / 加壳 / 加密"防误报"（反而更像恶意软件）、不要打包 `--key`、不要往包里塞自动更新器。

## 9. 优先级 3：跨平台基础

先看现状：**全仓库的平台判断只有 `backend/glass.py:37` 一处**（`sys.platform != 'win32'` 直接 return），`main.py` / `backend/api.py` 里没有 win32 硬编码，数据目录用的是 `Path.home()`。所以基础是干净的，**现在不需要为跨平台做任何重构**，只要别破坏下面三条边界。

| 平台 | 前端 dist | 后端 | 打包 | 障碍 |
|---|---|---|---|---|
| **Windows x64** | 通用 | 通用 | PyInstaller onedir | 本次已打通 |
| **macOS** | 通用 | pywebview 走 `cocoa`（WebKit）；`glass.py` 自动跳过 | PyInstaller **必须在 mac 上构建**（不能交叉编译） | 需要签名 + 公证（否则 Gatekeeper 拦）；想要毛玻璃得改用 pywebview 的 `vibrancy=True`（mac 专属参数），`backend/glass.py` 那条 DWM 路线在 mac 上是空操作 |
| **Linux** | 通用 | pywebview 走 GTK/QT，要系统库（`python3-gi` 等） | 建议 AppImage / Flatpak | 发行版差异大；`curl_cffi` 有 linux wheel |
| **Android** | 通用 | **不要走 pywebview 自带的那条**（`webview/platforms/android` 建在 Kivy + p4a + pyjnius 上，等于背两套 UI 栈）；推荐 **Chaquopy + AndroidX WebView + 本地 HTTP**（页面仍从 `127.0.0.1` 的静态服务来） | 需要在 Windows/Linux 上装 Android SDK/NDK + Gradle（Chaquopy 支持 Windows 构建） | **2026-10-14 复核后已改判**（原判"`curl_cffi` 没有 android wheel"已过期 —— PyPI 上有 `curl_cffi-0.16.3-cp314-cp314-android_24_arm64_v8a.whl`，Chaquopy 17.x 吃的就是这个 tag）：现在剩下的真难点是 ① 生命周期（没有"关窗"事件 → 进度落库时机 + 前台服务下载）；② 桥（54 个 js_api 方法要换成本地 HTTP JSON-RPC）；③ 触屏 UI（hover 显形 / 键盘 / 208px 固定左栏）；④ `pythonnet` 是 Windows/.NET 专属，`glass.py` / `desktop.py` 整块要门面化。**唯一必须真机验的总闸是"Chaquopy 装得上 curl_cffi 并直连图源"**（2026-10-15 已在模拟器 ARM 翻译层上验通）—— 详见 `tmp/安卓端技术栈与现状.md` |

**现在就守住的三条边界**（未来要不要做 mac/安卓，都不该破坏）：

1. **平台分支只许出现在 `backend/platform/` 门面里**（glass / 单实例 / 数据目录 / 窗口装饰都从这走），业务代码不许出现 `sys.platform`。
2. **数据与配置路径只有一个入口**（§4-P0-1 的 `backend/paths.py`）—— 今天 `~/.jmreader`，Android 上是 app 私有目录，换起来只改一处。
3. **网络层收口**（jmcomic client 的构造、curl_cffi 的 impersonate 参数集中在一处），将来 Android 换实现不用动业务。

**明确不建议现在做的**：为了"将来能上安卓"去引入 Kivy / p4a / Chaquopy。理由：Android 三件套（生命周期 / 桥 / 触屏 UI）都要重做，而且现在没有需求；等真要做时，**core（纯 Python 业务）+ 平台壳** 的重构会比现在猜着做省事得多。
